# M4 — Vertical slice, frontend — the first demoable state

**Model:** Sonnet. **Size:** L. **Previous:** M3 (vertical slice, backend).
**Demoable after:** **yes.** This is the first milestone that can be shown to a person: two browser
windows, an order created on POS-1, and the same order appearing on the kitchen screen through
PostgreSQL, the outbox, Redpanda, a consumer and a WebSocket.

## Goal

Close the loop that M3 left open at the database. M3 built HTTP → transaction → outbox → Redpanda →
kitchen consumer → `kitchen_tickets`. M4 adds the two halves that make it visible:

1. **Realtime out of the API process** — Socket.IO with the Redis adapter, plus the §12.2 realtime
   consumer that turns a Kafka message into a room broadcast.
2. **A Vue client** — a POS screen and a kitchen screen, both reusing the `@pos/contracts` types
   the API already returns, both treating a socket message as a *hint* and the HTTP snapshot as the
   truth.

Reads have to appear here too: M3 deliberately shipped no read endpoint, and neither screen can
render without one.

## Decisions this milestone must make before any code

### 1. The realtime consumer runs inside `apps/api`, on one shared consumer group

Socket.IO holds its connections in the API process. A consumer living in `apps/worker` would have
to reach those sockets over some second channel, which is the problem the Redis adapter already
solves — so the consumer runs **in the API process**, and the path is:

```
Kafka message -> realtime consumer (in api) -> io.to(rooms).emit -> Redis adapter -> every api instance -> browsers
```

**All API instances share one consumer group, `realtime`.** Each event is therefore delivered to
exactly one instance, which broadcasts it; the Redis adapter fans that broadcast out to sockets
attached to the *other* instances. This is the arrangement M14's multi-instance smoke test exists
to prove — a mutation applied via replica A must reach a client attached to replica B — and it is
only meaningful because the group is shared. Giving each instance its own group would deliver every
event to every instance, make the adapter dead weight, and leave M14 with nothing to assert.

Recorded as `docs/adr/006-realtime-consumer.md`. The ADR README currently reserves `006` for M5
under a different title; M4 takes the number and the README table is updated, because this is the
milestone that introduces the consumer.

**Consequence the code must respect:** the API now talks to Redpanda and Redis. Neither may become
a hard dependency. §17 is explicit — readiness checks **PostgreSQL only**, because the whole point
of the outbox is that a broker outage does not stop a POS taking orders. So:

- `buildApp()` stays pure — routes and the error handler, nothing more, so `fastify.inject` tests
  keep running with no broker and no Redis. The socket server and the consumer are wired in
  `src/index.ts`.
- The consumer start is retried in the background with bounded backoff and never blocks
  `app.listen()`. The worker's current "connect at startup or exit" behaviour is **not** copied
  here. (That the worker still behaves that way stays M6's open question.)
- The Redis adapter is attached with a client that reconnects on its own. With Redis down, a single
  API instance still broadcasts to its own sockets; only cross-instance fan-out degrades.

### 2. What the client filters, and why the crash window makes it mandatory

§12.2 records the event as processed and *then* emits, so a crash between the two loses that
broadcast forever. That is a real window and the client is what makes it survivable. Three rules,
all in the client:

- **Dedup by `eventId`.** A bounded set of recently seen ids; a repeat is dropped.
- **Ignore `version <= the version already held.`** This is what makes a duplicate emit harmless
  and what stops the echo of the client's own mutation from causing pointless work — the mutation
  response already carried the newer snapshot.
- **Refetch the canonical snapshot on reconnect**, not merely flip a badge to `CONNECTED`. Anything
  lost inside the crash window is repaired here.

Given those rules, **a socket message is treated as a trigger to refetch, not as data to apply.**
The client does not rebuild order state from event payloads: that would duplicate domain arithmetic
in the browser, and §13 explicitly says a snapshot refresh is sufficient and event-replay
infrastructure is not to be built. It also means M13's polling transport is the same code reached
by a different trigger, which is precisely §13's "both paths keep the UI correct; they differ only
in latency".

The gate is a pure function in its own module and is unit-tested. Without a test it would be an
assertion, and the crash window is the one place in this system where an untested client rule turns
into UI that silently disagrees with the database.

### 3. `GET /api/config` ships now, the rollout machinery does not

The client must not hardcode "open a socket". It fetches `GET /api/config?restaurantId=…` at
bootstrap and opens the socket only when `realtime.websocket_push` is on, showing the resolved
transport in the header.

What ships in M4 is a **direct read of the `feature_flags` table**. The Redis cache, the
percentage-by-hash rollout, the 15-second re-poll and the complete polling transport are M13 and
stay there. With the flag off in M4 the screens are still correct after every mutation and on
manual refresh, but receive no live updates — that gap is M13's to close and is stated here rather
than papered over.

### 4. Explicitly not in this milestone

Offline support, IndexedDB, the mutation queue, halt-on-conflict UI (M7, M8), `/debug` (M11),
`/demo` (M16), the remaining six mutation types and the kitchen commands (M5), the polling
transport (M13), rush-speed UX and BAR-1 (M15). `/debug` and `/demo` keep the M1 placeholder.

## In scope

### 1. `packages/config` — two new keys

- `REALTIME_CONSUMER_GROUP`, default `realtime`.
- `REALTIME_CONSUMER_RETRY_MS`, default `5000` — the backoff ceiling for the non-fatal consumer
  start described above.

Both added to `.env.example`.

### 2. `apps/api` — reads

All three are thin: a query, a mapping, and the §17 error envelope on failure. No business logic.

- `GET /api/menu` — the seeded products, ordered by name. `MenuItem` is a new `@pos/contracts`
  type so the client cannot drift from it.
- `GET /api/orders/:orderId` — the existing `loadOrderSnapshot`, returned as the `OrderSnapshot`
  the mutation response already carries. `404 ORDER_NOT_FOUND` when it does not exist.
- `GET /api/kitchen/tickets?restaurantId=…` — the `kitchen_tickets` projection, newest first.
  **This endpoint is an addition to the §17 list**, which has no read for the kitchen projection:
  `GET /api/restaurants/:restaurantId/orders` reads `orders`, and the kitchen screen must read the
  projection (§16) or its idempotency is not what is on screen. Recorded in `build-log.md`.
  `GET /api/restaurants/:restaurantId/orders` itself is not needed by any M4 screen and is not
  built here.
- `GET /api/config?restaurantId=…` — `{ restaurantId, flags: { 'realtime.websocket_push': boolean } }`,
  read straight from `feature_flags` per decision 3.

Query and path parameters are validated with zod exactly as the mutation route already does.

### 3. `apps/api` — Socket.IO and the realtime consumer

```
src/modules/realtime/socket-server.ts   attach socket.io to app.server, Redis adapter, subscribe
src/modules/realtime/broadcast.ts       roomsFor(event), the RealtimeEmitter interface
src/modules/realtime/consumer.ts        the §12.2 consumer: record, then emit
```

- **Rooms (§13):** `restaurant:{restaurantId}`, `order:{orderId}`, `kitchen:{restaurantId}`. The
  client sends a `subscribe` message naming its restaurant, its role (`pos` or `kitchen`) and its
  current order if it has one; the server joins the matching rooms and leaves the previous
  `order:` room. Room membership is derived on the server from that message — the client never
  names a raw room string.
- **`roomsFor(event)`** is a pure function: always `order:{aggregateId}` and
  `restaurant:{restaurantId}`, plus `kitchen:{restaurantId}` for `OrderSentToKitchen`. Socket.IO
  deduplicates a socket that belongs to several of the named rooms, so one emit reaches each client
  once.
- **The wire message** is the `DomainEvent` envelope on a single event name, `order.event`. One
  event name and one envelope means the client's dedup and version gate are written once rather
  than per event type.
- **The consumer, §12.2, in order:** `INSERT processed_events (event_id, 'realtime') ON CONFLICT DO
  NOTHING`; no row inserted means a duplicate and nothing is emitted; otherwise emit. The commit
  happens before the emit and the comment in the code says plainly that a crash between them drops
  that broadcast, and names the client rules from decision 2 as the mitigation. It does **not**
  pretend to be transactional.
- The consumer's `groupId` is `REALTIME_CONSUMER_GROUP`, distinct from the kitchen consumer's, so
  the two have independent offsets and neither starves the other.
- `handleRealtimeEvent(db, emitter, event)` is exported separately from the Kafka plumbing so it
  can be tested against a real PostgreSQL and a fake emitter, with no broker.

### 4. `packages/contracts` — the shared client vocabulary

`MenuItem`, `KitchenTicket`, `ConfigResponse`, and `REALTIME_EVENT_NAME` / the `subscribe` payload
type. The client imports these; it does not restate the API's shapes. `MutationRequest`,
`MutationResponse` and `OrderSnapshot` already exist and are reused as they are.

### 5. `apps/web` — two screens

New dependencies: `@pos/contracts` (workspace) and `socket.io-client`.

```
src/api/client.ts            typed fetch for the four reads and the one write
src/realtime/event-gate.ts   dedup by eventId + the version gate  (pure, tested)
src/realtime/socket.ts       connect, subscribe, reconnect callback
src/stores/menu.ts           the product list
src/stores/order.ts          the current order snapshot + the mutation calls
src/stores/kitchen.ts        the ticket list
src/stores/connection.ts     online / socket status / transport
src/views/PosView.vue
src/views/KitchenView.vue
src/components/StateBadge.vue
```

- **POS (`/pos/:terminalId`)** — terminal name, the restaurant it belongs to, socket status,
  transport (`PUSH` / `PUSH DISABLED`), the current order with its **version badge**, the menu, and
  the actions this milestone supports: **create order** (client-generated `orderId`, `CREATE_ORDER`
  at `baseVersion: 0`), **add item**, **send to kitchen**. `baseVersion` always comes from the
  snapshot the client holds; every request carries a fresh `mutationId` (`crypto.randomUUID()`).
  A `CONFLICT` response replaces the local snapshot with `canonicalOrder` and shows the reason —
  the queue-halting resolution UI is M8.
  The terminal-to-restaurant mapping comes from the seeded terminals; `pos-3` therefore shows
  `second-restaurant`, which is what makes the tenant story visible later.
- **Kitchen (`/kitchen`)** — the tickets from the projection, one card per order with its table
  number, items and the `source_event_version` it was built from. A single `NEW` column: the
  `PREPARING` and `READY` columns and their commands are M5's, when `START_PREPARING` and
  `MARK_READY` become real mutations. Building empty columns now would advertise buttons that
  cannot work.
- **Both screens** apply decision 2: the socket message passes the gate, and a message that passes
  triggers a snapshot (or ticket-list) refetch. `connect` and `reconnect` refetch unconditionally.
- Styling stays at "legible": Tailwind, the neutral palette already in `App.vue`, no design work.
  M15 owns the rush-speed UX.

### 6. Tests

Narrow, and only where the test proves something a reader would otherwise have to take on faith.

`pnpm -F @pos/api test` (adds to the existing suite):

- `GET /api/menu` returns the seeded products.
- `GET /api/orders/:id` returns the snapshot for a created order and `404 ORDER_NOT_FOUND`
  otherwise.
- `GET /api/kitchen/tickets` returns only the requested restaurant's tickets.
- `GET /api/config` reflects the flag row.
- **The realtime consumer is idempotent and honest:** the same event handled twice emits once and
  writes one `processed_events` row for the `realtime` consumer, and does not disturb the
  `kitchen` consumer's row for the same event.
- `roomsFor` puts `OrderSentToKitchen` in the kitchen room and everything else in exactly two.

`pnpm -F @pos/web test` (new — vitest, one file):

- the event gate: a duplicate `eventId` is dropped, a `version` at or below the held version is
  dropped, a newer version passes, and the seen-set stays bounded.

No test opens a socket or a broker connection. The real round trip is the Verification block below,
run by the user, and is automated by `pnpm verify:integration` in M6.

## Verification

Claude runs, against the PostgreSQL the user already has up:

```bash
pnpm typecheck
pnpm lint
pnpm build
pnpm -F @pos/api test
pnpm -F @pos/web test
```

All green: 62 tests (9 domain, 27 api, 11 worker, 15 web).

The user then confirms the demo, with `pnpm dev` running and Compose up:

1. Open `http://localhost:5173/pos/pos-1` and `http://localhost:5173/kitchen` side by side.
2. On POS-1: create an order, add two items, check the version badge climbs 1 → 2 → 3 and the
   total is right.
3. Press **Send to kitchen**. The ticket appears on the kitchen screen **without a reload**, within
   about a second, carrying the same table number and items.
4. Open `http://localhost:5173/pos/pos-2`, create a second order there, send it, and confirm both
   tickets are on the kitchen screen.
5. Stop the worker (`pnpm -F @pos/worker dev` interrupted), send a third order from POS-1: the POS
   still accepts it — the write path never touched the broker. Start the worker again and the
   ticket arrives. This is the outbox doing its job, visible on screen.
6. `pnpm db:check` — one `kitchen_tickets` row per sent order, `processed_events` rows for both the
   `kitchen` and the `realtime` consumer.

## Review — accepted after the first commit

Six findings, four of them correctness holes the milestone's own tests did not reach. All are
implemented; the reasoning is in `build-log.md` and the durable facts are in `PROGRESS.md`.

1. **The broadcast can outrun the projection** (P1). Two consumer groups, nothing ordering them.
   The kitchen refresh now takes the event and reads until `source_event_version >= event.version`
   on a bounded backoff. The kitchen also stopped joining `restaurant:{id}`, because events it can
   never converge on were waking that wait.
2. **`GET /api/orders/:id` was not a consistent read** (P1). Two SELECTs at READ COMMITTED. Now
   `repeatable read`, `read only`.
3. **The realtime consumer never recovered from a crash** (P1). Now envelope-validated (poison
   messages are skipped, not thrown) and supervised through `consumer.events.CRASH`.
4. **A retried creation could make a second order** (P1). The client keeps the identity of an
   unanswered mutation and reuses it, so §9 resolves the retry.
5. **An older refetch could roll the screen back** (P2). `adopt` is monotonic per order.
6. **A slow `start` leaked past `stop`** (P2). Both claim a generation.
