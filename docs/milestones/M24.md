# M24 — The deployment surface

The last pass of *The second sweep* (`MILESTONES.md`), and the last three lines of the seventeen.
All three are `[M14, P3]`s, and they share the property that makes this milestone unlike M21–M23:
**nothing in `pnpm test` can reach any of them.** They live in a config file nginx reads, a
healthcheck Docker runs and a workflow GitHub runs. The Verification block is the whole proof, and
it needs Compose.

A milestone here is finished when its lines are **gone** from `known-problems.md` — deleted if
fixed, moved up into *Accepted limits* if the honest answer is that the behaviour is right.

## The three

1. **`[M14, P3]`** — `apps/web/nginx.conf`. nginx resolves `api-1` and `api-2` **once, when it loads
   its config**, so a replica recreated with a new address is proxied to the old one until nginx is
   reloaded. The same defect has a second face: the web image **cannot start at all** outside the
   Compose network, because that load-time resolution fails and nginx refuses the config.
2. **`[M14, P3]`** — `docker-compose.multi.yml`. `worker-prod` declares no healthcheck, so
   `up --wait` proves the container is *running*, not that the publisher is turning. What actually
   covers it today is the smoke test's own round trip, which means a worker that started and died
   is reported as a **broadcast** failure — the §19.10 assertion blaming the thing it is testing.
3. **`[M14, P3]`** — `.github/workflows/ci.yml`. The `images` job builds three images and starts
   none, and the bases float on `node:24-alpine` / `nginx-unprivileged:1.29-alpine` rather than
   digests. A green build is not a green start.

## The shape of the fix

**1 and 3 are one argument.** The reason CI cannot start the web image is the reason a recreated
replica is proxied to a dead address: resolution at config-load time. Fix it and the CI step becomes
possible; add the CI step and the fix has something that fails without it. Verified locally, before
either was written:

```
nginx: [emerg] host not found in upstream "api-1:3000"    # today, nginx -t on the built image
nginx: configuration file /etc/nginx/nginx.conf test is successful   # with resolve
```

The fix is **not** a variable `proxy_pass`, which is the obvious one and wrong twice: a variable
target **drops the URI** (the path has to be written back with `$request_uri`), and it cannot name
two servers, so `ip_hash` goes with it — and `ip_hash` is load-bearing for the Socket.IO polling
handshake (the comment at the top of the file says why). Instead: `resolver`, an upstream `zone`,
and `resolve` on each `server`. That parameter was nginx Plus-only until 1.27.3; the image is
**1.29.8**, and the config above was tested in it.

**2** needs the worker to have a surface to probe, and it has none — which is also why
`verify-e2e.mjs` waits on a log line instead. So a health server: `node:http`, two routes, opt-in on
`WORKER_HEALTH_PORT` being set. Opt-in is not timidity — `verify:e2e` starts a worker beside a demo
worker the user may already have up, and a second process binding the same port would turn a fix
into a regression. Readiness answers one question, *is the publisher turning*, which is
`brokerConnected && publisherPassCompleted && printWorkerRunning`.

That predicate is a pure function over a state object, so it is the one part of this milestone a
vitest **can** reach — and the http surface is testable on port 0.

## Scope

The three above, plus the two leftovers from M21 and M22 that live in the same two files, both
cheap:

- `verify-e2e.mjs` probes `:3000` **after** Chromium, the build, the migration and the seed, so a
  user who left an API up waits two minutes to be told to stop it. Move the probe first.
- `docker-compose.multi.yml` names `pos_multi`, which only `verify-multi-instance.mjs` creates, so
  bringing the overlay up by hand starts two replicas against a database that does not exist. An
  init script under `postgres` is the fix — and it must stay idempotent, because the script still
  creates it for the volume the user has had since M1.

Not in scope: the two M22 flag-cache P3s (a different surface, and both unreachable as deployed).

## Verification

The first four need infrastructure, and **the user brings it up** (CLAUDE.md rule 3) — never a live
container log.

1. `docker run --rm -v .../nginx.conf:/etc/nginx/conf.d/default.conf:ro
   nginxinc/nginx-unprivileged:1.29-alpine nginx -t` **succeeds** outside any Compose network. It
   fails on the pre-M24 file. *(Run locally; done, output above.)*
2. `pnpm verify:multi --keep`, then `docker compose ... up -d --force-recreate api-2`, then
   `:8081/api/health/ready` through nginx still answers on every request. Pre-M24 half of them
   reach a dead address.
3. `docker compose -f docker-compose.yml -f docker-compose.multi.yml up -d --wait worker-prod` with
   `KAFKA_BROKERS` pointed at nothing **times out** instead of reporting success.
4. `docker compose -f docker-compose.yml -f docker-compose.multi.yml up api-1` on a **fresh volume**
   reaches readiness without `verify:multi` having been run first.
5. `pnpm -F @pos/worker test` — the readiness predicate and the two routes.
6. `pnpm lint && pnpm typecheck && pnpm test && pnpm build`.
7. The three CI smoke commands, run by hand against `pos-*:local`, since a workflow cannot be run
   locally: the api image serves `/api/health/live` and **refuses** `/api/health/ready` with no
   database; the worker image reaches its first query (proving the pruned tree resolves); the web
   image serves `/`.

## Traps

- `nginx -t` **succeeding** is itself the signal that resolution is deferred. If it still resolves
  at load time the test would fail outside Compose, which is exactly the pre-M24 behaviour.
- The worker health server must not make `verify:e2e` or `pnpm dev` bind a port. No default.
- `docker/build-push-action` with `push: false` and no `load: true` leaves the image **in the
  builder cache and not in the daemon** — `docker run pos-api:ci` would say "no such image".
- With an empty environment `@pos/config` defaults everything, so an image started with no env does
  not fail at configuration: the api *listens*, and the worker gets as far as its first query. Both
  facts are what the smoke steps assert; neither is a config-validation check.
- The digests are index digests (multi-platform), resolved with
  `docker buildx imagetools inspect <tag> --format '{{.Manifest.Digest}}'`. Keep the tag beside the
  digest, and keep the `deps` stage byte-identical across the three Dockerfiles (BuildKit shares one
  `pnpm install` across them only while that holds).
