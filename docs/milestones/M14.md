# M14 — Production images and the multi-instance smoke test

§22 in full: a multi-stage Dockerfile per app, non-root, built output only; a Compose overlay
running **two addressable API replicas** behind the Redis adapter; and a test that asserts a
mutation applied through replica A reaches a WebSocket client attached to replica B (§19.10).
Model **Sonnet**, size **M**.

The point of the milestone is one sentence: §13 has claimed cross-instance broadcast since M5 and
nothing has ever proved it. **The smoke test is the deliverable.** The images exist to make two
replicas runnable, and they are also what §22 asks for in their own right.

## The path the event actually takes

Worth writing down before designing the test, because it is not the obvious one. Nothing in
`apps/api` broadcasts from the mutation handler: `grep` for `RealtimeEmitter` and the only
producer is `modules/realtime/consumer.ts`. So the full path is

```
POST /api/orders/:id/mutations → replica A → outbox row (same transaction)
  → worker (single instance) → Kafka → realtime consumer group
  → whichever replica holds the partition → io.to(rooms).emit → Redis adapter → every replica
```

Two consequences:

1. **The stack under test is the whole stack** — postgres, redis, redpanda, two APIs *and* the
   worker. There is no shortcut where the API talks to itself.
2. **Which replica consumes is not ours to choose.** Both replicas join
   `REALTIME_CONSUMER_GROUP`, so exactly one gets the message. Asserting only "B receives it"
   would pass without any cross-instance hop whenever B happened to be the consumer.
   So the test **attaches a client to each replica and asserts both receive the event**: whichever
   one consumed, the other one's delivery crossed Redis. That is deterministic; asserting one side
   is a coin flip.

## The images

One `Dockerfile` per app, context = repository root (a per-app context cannot resolve `@pos/db`).

- Stage `deps` — copy the lockfile and **every** `package.json`, then `pnpm install
  --frozen-lockfile`. Keep this stage byte-identical in all three files so BuildKit's content
  cache is shared between them; otherwise three images means three full installs.
- Stage `build` — copy sources, `pnpm run build:packages` then the app's own `build`, then
  `pnpm install --frozen-lockfile --prod --ignore-scripts` to prune devDependencies in place.
- Stage `runtime` — `node:24-alpine`, `USER node`, and only `dist/`, `package.json` and the pruned
  `node_modules` (root, `packages/*` and the app's — pnpm's symlinks are relative and survive
  `COPY --from`). `tsup` marks `dependencies` external, so `dist/index.js` alone is not runnable;
  the `node_modules` tree is not optional.
- `apps/web` builds with Vite and is served by `nginxinc/nginx-unprivileged` — an unprivileged
  nginx by construction, rather than the usual root-nginx-with-a-`USER`-line that cannot bind 80.
  It fronts **both** replicas as one upstream, which is what makes §19.10 visible in a browser.
  The upstream is `ip_hash`: the client asks for `websocket` first but keeps `polling` as a
  fallback, and a polling handshake round-robined across two replicas fails on the second request.

Add a root `.dockerignore` (`node_modules`, `dist`, `.git`, `.verify-output`) or the build context
is the whole workspace including every `node_modules`.

## The overlay

`docker-compose.multi.yml`, used with the base file, adds **new service names** rather than
overriding `api`/`web`/`worker`. The base app services mount `.:/workspace` and run `tsx`, and
Compose merges `volumes` by appending — an override could add a mount but could never remove one,
so the production image would run with the source tree mounted over it. Hence `api-1`, `api-2`,
`worker-prod`, `web-prod`.

- `api-1` on host `3001`, `api-2` on `3002` — **addressable separately**, which is why this is two
  services and not `deploy.replicas: 2`. The test has to name A and B.
- `worker-prod` stays **one** instance (see PROGRESS.md: a second publisher would change what
  `/debug`'s backlog numbers mean).
- Healthchecks on `/api/health/ready` so `--wait` is the readiness gate, exactly as the base file
  already does for the infrastructure.

Two things will look wrong in a two-replica run and are correct: `socketCount()` is per instance
by design, and so is the M11 in-process counter registry — `/debug` shows whichever replica
answered. The comments in `socket-server.ts` and `debug/application/counters.ts` say why.

## The test and its runner

`apps/api/test/multi-instance.integration.test.ts`, behind its own
`vitest.integration.config.ts`, exactly as `@pos/worker` already does — and the default
`vitest.config.ts` gains an `exclude` so `pnpm -F @pos/api test` stays runnable against a database
alone. `socket.io-client` becomes an `@pos/api` devDependency.

`beforeAll` sends one throwaway `CREATE_ORDER` and waits for it on either socket. That is the
kafkajs group join and the first rebalance, which take seconds; paying for them once, explicitly,
beats a sleep that is either too short on CI or wasted locally.

`scripts/verify-multi-instance.mjs` is the runner, and it is the same shape as
`verify-integration.mjs`: bring up, migrate and seed, run, tear down **only what it started**,
write to `.verify-output/multi-instance.log`. The two scripts now share
`scripts/lib/compose-run.mjs` — the duplication is the concrete problem that justifies the
extraction, and the alternative is 150 copied lines that will drift.

## Deliverables

- `apps/{api,worker,web}/Dockerfile`, `apps/web/nginx.conf`, root `.dockerignore`.
- `docker-compose.multi.yml`.
- `scripts/lib/compose-run.mjs`, `scripts/verify-multi-instance.mjs`, and
  `verify-integration.mjs` refactored onto it. Root script `verify:multi`.
- `apps/api/test/multi-instance.integration.test.ts` + `apps/api/vitest.integration.config.ts` +
  `exclude` in `apps/api/vitest.config.ts` + `test:integration` script.
- CI: a job that builds the three images. Not the smoke run — it needs the whole stack and CI
  already owns one Compose lifecycle.
- `docs/adr/016-production-images.md` if the image layout needs an argument (it does: why the
  workspace tree ships rather than a bundled single file).
- `docs/known-problems.md`: P2/P3 from the one review pass.

## Verification

1. `pnpm run build:packages && pnpm lint && pnpm typecheck && pnpm build`
2. `pnpm -F @pos/api test` — unchanged count, the new file excluded.
3. `pnpm verify:integration` — proves the refactor did not break the existing runner.
4. `pnpm verify:multi` — **the milestone**: images build, both replicas come up healthy, and the
   §19.10 test passes on both sockets.
