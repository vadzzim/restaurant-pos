# M1 — Baseline commit, monorepo, infrastructure

**Model:** Sonnet. **Size:** M. **Previous:** M0 (documents only). **Demoable after:** no.

## Goal

`pnpm install && pnpm typecheck && pnpm lint && pnpm build` pass on an empty skeleton, and
`docker compose up -d` brings up postgres, redis and redpanda. All three application processes
exist, start, and log that they are alive. There is no business logic.

## In scope

### Step 0 — git baseline, before any code

`git init`, write `.gitignore`, then commit the M0 documents on their own:

```
git commit -m "M0: spec, milestone plan, conventions"
```

The M0 documents were written before the repository existed, so `MILESTONES.md` marked M0 done
with nothing recorded in git. This commit makes that marker honest and gives every later milestone
a clean point to reset to. Only then start the M1 work below, which gets its own commit at the end.

`.gitignore`: node_modules, dist, .env, .turbo, coverage, playwright-report, `*.log`,
`.verify-output/`.

### The skeleton

1. `pnpm-workspace.yaml` covering `apps/*` and `packages/*`.
2. A root `package.json` whose scripts orchestrate the workspaces:
   `dev lint typecheck test build db:migrate db:seed`. The last two proxy into the api workspace
   for now and fail with a clear "M2 not implemented" message rather than silently.
3. `tsconfig.base.json`: strict, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, ESM,
   and path aliases for `@pos/contracts`, `@pos/domain`, `@pos/config`.
4. ESLint (typescript-eslint, flat config) plus Prettier, with a rule forbidding `any`.
5. `packages/config`: a zod schema for the environment, a single place that reads it, and a typed
   export. No direct `process.env` access anywhere else in the codebase.
6. `packages/contracts`: for now only `DomainEvent<T>`, `OrderStatus` and `MutationType` from
   §3, §5 and §11 of the spec. `MutationType` must already be the complete list —
   `CREATE_ORDER | ADD_ITEM | REMOVE_ITEM | CHANGE_QUANTITY | SEND_TO_KITCHEN | START_PREPARING |
   MARK_READY | PAY | CANCEL`. Kitchen transitions are mutations, not a side door, and **order
   creation is a mutation too**, with a client-generated `orderId` and `baseVersion: 0` — there is
   no separate creation endpoint anywhere in this project.
   `packages/domain`: an empty index sketching the intended structure. This is not critical
   functionality yet, so a stub is acceptable here specifically.
7. `apps/api`: Fastify, a pino logger, graceful shutdown, and stubbed health routes
   `GET /api/health/live` and `GET /api/health/ready` both returning `{status:'ok'}`. The real
   dependency checks and the three-way split land in M6 — but the route shapes are created now so
   nothing has to be renamed later.
8. `apps/web`: Vite + Vue 3 + TS + Tailwind, a router with placeholder routes for
   `/pos/:terminalId`, `/kitchen`, `/debug` and `/demo`, a redirect from `/` to `/pos/pos-1`, and
   a dev proxy from `/api` to the api process.
9. `apps/worker`: a process logging a heartbeat every ten seconds, with graceful shutdown.
10. `docker-compose.yml`:
    - `postgres:16` with a `pg_isready` healthcheck, a named volume, port 5432;
    - `redis:7` with a `redis-cli ping` healthcheck, port 6379;
    - `redpanda` (image `redpandadata/redpanda`) in single-node mode, port 9092, healthcheck;
    - `redpanda-console` on port 8080, so events can be shown on screen during the interview;
    - `api`, `web` and `worker` under an `app` profile with `depends_on: service_healthy`, so that
      a plain `docker compose up -d` starts only the infrastructure and the application runs
      locally via `pnpm dev` during development.
11. `.env.example` and `.env` with identical contents — no secrets, this is a demo.
12. A short `README.md` covering startup and URLs. The full README is M19's job.

## Out of scope

The database schema, migrations, Drizzle, Socket.IO, KafkaJS, BullMQ, real health checks, the POS
UI, the CI workflow (M6), `pnpm verify:integration` (M6), production Dockerfiles and the
multi-instance overlay (M14). Each belongs to its own milestone.

## Decisions to record as ADRs

- `docs/adr/001-modular-monolith.md` — three processes, not microservices.
- `docs/adr/007-drizzle.md` — why Drizzle rather than Prisma (explicit concurrency-sensitive SQL).

## Verification

Claude runs:

```bash
pnpm install
pnpm typecheck
pnpm lint
pnpm build
```

All four must be green. `pnpm test` may report that there are no tests — that is expected at M1.

The user runs and confirms:

```bash
docker compose up -d
```

Expected: `postgres`, `redis`, `redpanda` and `redpanda-console` all healthy, with
`docker compose ps` showing four containers. Then, locally:

```bash
pnpm dev
```

and in the browser: `http://localhost:5173/pos/pos-1` renders the placeholder,
`http://localhost:3000/api/health/ready` returns `{"status":"ok"}`, the worker log shows a
heartbeat, and `http://localhost:8080` opens the Redpanda console.

If anything fails, the user pastes twenty lines of the error and Claude fixes it.

## Definition of done

- The M0 baseline commit exists and precedes any code.
- All four commands green.
- The user has confirmed the infrastructure and all three processes start.
- `docs/PROGRESS.md` updated: what is done, what is next, problems, and the first command for the
  following session.
- `docs/build-log.md` appended to if anything broke.
- Both ADRs written.
- Do NOT create `docs/milestones/M02.md` — the next session expands it.
- Commit: `git add -A && git commit -m "M1: monorepo, docker compose, three app processes"`.
