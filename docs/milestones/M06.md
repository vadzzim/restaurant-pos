# M6 — Error model, logging, split health, CI

**Model:** Sonnet. **Size:** M. **Previous:** M5 (all nine mutations, the full §8 matrix).
**Demoable after:** yes — the same demo as M5, plus one new thing worth showing: **stop Redpanda
and the POS keeps taking orders**, with `/api/health/ready` still green and
`/api/debug/dependencies` naming exactly what is degraded.

## Goal

M6 does not add a feature. It closes the operational half of the system: the error model, the
correlation fields, the three-way health split, and the one command that reproduces the whole thing
from a clean checkout.

**Almost everything here already exists in outline.** `ApiError` and a single error handler are in
`apps/api/src/shared/errors.ts` and `buildApp()`. `/api/health/live` and `/api/health/ready` are
routes that return `{status:'ok'}` without checking anything. `executeMutation` already logs a
mutation with a `traceId`. `GET /api/config` already resolves feature flags. M6 finishes each of
them rather than inventing it, and adds the two things that genuinely do not exist yet:
`pnpm verify:integration` and CI.

## In scope

1. **A typed error model.** `ApiErrorCode` as a closed union, a `validationFailed` helper so five
   routes stop repeating the same six lines, and an error handler that also handles the two cases
   it currently mishandles: a Fastify-generated error (malformed JSON) and an unknown route.
2. **Correlation fields on every log line** — `requestId` and `traceId` bound to the per-request
   child logger, and the full §20 field set on the mutation log line, **in `executeMutation`**,
   which is the one place all three write routes pass through.
3. **The traceId reaches the events.** `x-trace-id` on the request becomes
   `outbox_events.trace_id`, which the publisher copies onto the `DomainEvent`, which both
   consumers already log. One header, followed end to end across three processes.
4. **The three-way health split of §17**: `live` (nothing), `ready` (PostgreSQL only, 503 when it
   is down), and `debug/dependencies` (Postgres, Redis, Redpanda, outbox backlog, hard vs soft).
5. **The worker's broker dependency is supervised**, closing the open question in `PROGRESS.md`.
6. **`pnpm verify:integration`** — one script: Compose up, wait for healthy, run the suites that
   need infrastructure, tear down what it started, write everything to a file.
7. **One real Redpanda round trip in the test path**, so `verify:integration` verifies something
   `pnpm test` cannot: outbox row → producer → broker → consumer group → projection.
8. **`.github/workflows/ci.yml`** — lint, typecheck, unit tests, `verify:integration`, build. No
   `services:` block.
9. **`docs/adr/011-health-and-degradation.md`.**

## Out of scope

- **No M13 in `GET /api/config`.** It stays the M4 stub: a direct read of `feature_flags`, no Redis
  cache, no percentage rollout, no 15-second client poll. M6's brief lists the route because §17
  lists it and it must exist; it exists. Widening it here would spend M13's milestone early and
  leave the polling transport — the flag's other, complete branch — still unbuilt.
- **No `/api/debug/{events,conflicts,outbox,metrics}` and no counters.** M11 owns §20's counters and
  the `/debug` page. M6 builds `dependencies` only, because §17 defines it as the third leg of the
  health split, not as a debug panel.
- **No consumer lag number.** It needs a Kafka admin describing group offsets, and it belongs next
  to the other counters in M11. The dependency report says so in place of guessing.
- No offline queue (M7/M8), no outbox backoff hardening (M9), no print job (M10).
- **No re-review of M5.** Two Codex rounds landed at `b15e56a` and `c8dde81`; their residues are in
  `PROGRESS.md` under Known problems and stay there.

## Decisions this milestone must make before any code

### 1. The error envelope is for transport failures. §5 outcomes are not errors

§17 shows `{"code": "ORDER_VERSION_CONFLICT", ...}` as the error example, which reads as though a
version conflict should travel in the error envelope. It must not, and the code already agrees:
§5 defines the mutation response explicitly, the client discriminates on `status`, and
`packages/contracts` already carries the comment "Domain outcomes above are not errors and never
use this shape."

A conflict is a **successful** application of the rules — the server did exactly what it should and
has a snapshot to hand back. Routing it through the error handler would erase the snapshot, erase
the `reason`, and make the one response the offline queue has to branch on (§14.1) look like a
failure. So: `ApiErrorCode` covers `VALIDATION_FAILED`, `ORDER_NOT_FOUND`, `ROUTE_NOT_FOUND` and
`INTERNAL_ERROR`, and nothing that `decide()` can produce.

### 2. Two error paths currently produce the wrong body, and that is what "typed and complete" means

- A malformed JSON body makes Fastify throw `FST_ERR_CTP_INVALID_JSON`, which carries
  `statusCode: 400`. The current handler only recognises `ApiError`, so it answers **500
  `INTERNAL_ERROR`** — telling the client its own bad request was a server fault, which under
  §14 is the difference between "fix the payload" and "retry forever".
- An unknown route gets Fastify's default 404 body `{message, error, statusCode}`, which is not the
  §17 envelope at all.

Both are fixed by the handler, not by the routes: honour `error.statusCode` when a Fastify error
carries a 4xx one, and add `setNotFoundHandler`. This is the whole of "backed by typed domain
errors": the envelope is produced in exactly one place and there is no way out of the API that
bypasses it.

### 3. `traceId` and `requestId` are two fields, and one of them may come from the client

`requestId` identifies **this HTTP call**; `traceId` identifies **the work**, and the work outlives
the call — it becomes an outbox row, a Kafka message, a projection write and a broadcast. So:

- `requestId` = `request.id`, seeded from `x-request-id` when the client sends one.
- `traceId` = `x-trace-id` when the client sends one, **otherwise the requestId**. No second
  generated id: when nothing upstream is tracing, the request *is* the trace, and inventing a
  distinct uuid would add a field that correlates with nothing.

Both are bound once, in an `onRequest` hook, onto the request's child logger — so every line
Fastify itself emits carries them too, not only the lines this code writes.

### 4. The correlation fields go in `executeMutation`, and nowhere else

Three routes construct mutations: `POST /api/orders/:orderId/mutations` and the two kitchen
adapters. All three already hand off to `executeMutation`, which exists precisely so that they stay
indistinguishable to a client. Logging in three route handlers would be three copies that drift;
the second time a field is added, one of them would be missed. One call site, all of §20's fields
that a mutation can know.

One refinement: the level follows the outcome. `APPLIED` and `ALREADY_APPLIED` are `info`;
`CONFLICT`, `REJECTED` and `MUTATION_ID_REUSED` are `warn`. A run of conflicts is the signal an
operator is looking for, and it should be visible without reading every applied mutation.

### 5. `ready` checks PostgreSQL, and its failure body has the same shape as its success body

`/api/health/ready` runs `select 1` and answers 200 or **503** — a readiness probe that always
answers 200 is not a probe. It does **not** use the error envelope, in either direction: a probe
response is a report, and the same shape on 200 and 503 means the human reading a failing probe
sees which check failed rather than a generic code. This is the ADR's subject and is argued there.

### 6. The dependency report grades hard against soft, because that is the entire point

`/api/debug/dependencies` reports each dependency with a `kind`:

- `postgres` — **hard**. Down means the API cannot accept a write. Readiness fails.
- `redis` — **soft**. Down means cross-instance broadcast fan-out degrades; an instance still
  reaches its own sockets, and writes are untouched.
- `redpanda` — **soft**. Down means events accumulate in the outbox and screens stop updating live.
  **Orders are still accepted.** This is the sentence the whole architecture exists to make true.

The top-level `status` is `ok` when everything is up, `degraded` when only soft dependencies are
down, and `unavailable` when a hard one is. `degraded` is the state the demo is *for*; a report
that could only say "healthy" or "broken" would flatten the one distinction worth showing.

Each probe carries its own timeout, so one unreachable dependency cannot make the report that
explains it hang. The report also carries the outbox backlog (`pending`, `deadLettered`, and the
age of the oldest unpublished row), because "Redpanda is down" and "and 47 events are waiting" are
one thought.

`buildApp()` stays routes-only (ADR 006). It takes the Postgres probe from the `db` it already has
and accepts the others as parameters, so `fastify.inject` tests need neither Redis nor a broker —
and a test that passes a failing probe can assert the `degraded` branch deterministically.

### 7. The worker gets the same supervision as the API, and for a sharper reason than symmetry

The open question in `PROGRESS.md`: the worker exits when Redpanda is down at startup, while the
API retries in the background. Give it the same treatment — but the naive form of "the same
treatment" is wrong, and the difference is the interesting part.

The API's consumer is supervised because the API has other work to do without it. The worker
apparently does not: both its jobs need the broker. So "just let it run and let the publisher fail"
looks equivalent to retrying. It is not. **The publisher's failure path is not free** — each failed
pass increments `attempt_count`, and at the current settings (8 attempts, backoff capped at 60 s) a
broker outage of roughly three minutes would **dead-letter perfectly good events**. Dead-lettering
is supposed to mean *this event is bad*, and M9 and §18 both build on that meaning.

So the worker supervises its broker connection **and does not start work it cannot do**: the
publisher loop only runs while a producer is connected. With Redpanda down the worker stays alive,
retries the connection with backoff, and leaves the outbox exactly as it is — rows unpublished,
`attempt_count` untouched. When the broker returns, the backlog drains.

Exiting was the third option and is the worst of the three here: Compose declares no restart policy
for the dev services, so the process would simply be gone, and the demo's recovery story would
require a human to notice and restart it — which is precisely the half-dead state the API's
supervisor was written to avoid.

### 8. `verify:integration` tears down only what it started

The user keeps Compose up for the demo (`CLAUDE.md`). A script that unconditionally runs
`docker compose down` would destroy the running demo as a side effect of running the tests. So the
script records which of `postgres redis redpanda` were already running, and removes only the ones
it brought up itself. It never touches volumes, so the demo database survives either way — and the
suites truncate `pos_test`, never `pos`.

It is a Node script, not a shell script: the user is on Windows, CI is on Linux, and one file that
runs on both beats two that drift.

### 9. `pnpm test` must stay runnable with only PostgreSQL

Today every suite needs Postgres and nothing needs a broker. Adding the round-trip test to the
default run would make `pnpm -F @pos/worker test` fail on a machine with no Redpanda, which is a
worse trade than an extra config file. So the round trip lives in
`apps/worker/test/kafka-roundtrip.integration.test.ts`, excluded from the default run and included
by `vitest.integration.config.ts`, which `verify:integration` invokes as a separate step.

It publishes to **its own topic and its own consumer group**, both suffixed per run. A test that
used `restaurant.order.events` would be consumed by the worker the user has running against the
demo database, and would write kitchen tickets for orders that do not exist there.

## Verification

```
pnpm run build:packages
pnpm typecheck && pnpm lint
pnpm -F @pos/api test
pnpm -F @pos/worker test
pnpm build
pnpm verify:integration
```

- `GET /api/health/live` answers 200 without touching the database — asserted against an app whose
  Postgres probe is rigged to fail.
- `GET /api/health/ready` answers 200 with a live database and **503** with a failing Postgres
  probe, both in the same body shape.
- `GET /api/debug/dependencies` reports `degraded` when a soft probe fails and `unavailable` when
  the hard one does, and carries the outbox backlog.
- A malformed JSON body answers **400 `VALIDATION_FAILED`**, not 500.
- An unknown route answers **404 `ROUTE_NOT_FOUND`** in the §17 envelope.
- `x-trace-id` on a mutation request is written to `outbox_events.trace_id`.
- The round-trip test: an outbox row published by the real producer reaches a real consumer group
  through Redpanda and becomes a `kitchen_tickets` row, and the outbox row is marked published.
- `pnpm verify:integration` exits 0 and leaves its full output in `.verify-output/integration.log`.

Manual, once, with the user driving Compose: stopping `redpanda` leaves `/api/health/ready` at 200,
`/api/debug/dependencies` at `degraded`, and a mutation still returns `APPLIED`.

## Definition of done

- Every response leaving the API is either a §5 domain outcome, a §17 error envelope, or a health
  report — there is no fourth shape and no stack trace in any of them.
- Every log line from an HTTP request carries `requestId` and `traceId`; a mutation's line carries
  the whole §20 set that a mutation can know; and that `traceId` is on the event the consumers log.
- Readiness fails when PostgreSQL is down and only then. Redpanda down is `degraded`, never
  unready, and orders are still accepted.
- The worker survives a broker outage without dead-lettering an event over it.
- `pnpm verify:integration` reproduces the whole thing from a clean checkout, and CI runs that same
  command with no `services:` block.
- ADR 011 is written, `PROGRESS.md` and `build-log.md` are updated, and the tree is one commit.
