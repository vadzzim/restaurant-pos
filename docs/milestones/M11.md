# M11 — The debug dashboard

**Model:** Sonnet. **Size:** M. **Previous:** M10 (the BullMQ print job) plus its review rounds.
**Demoable after:** yes — `/debug` populates against live traffic, and every number on it is
labelled with where it comes from.

## Goal

`/debug` is the first screen that reads across every subsystem, so the risk is the shape, not the
SQL. Five endpoints (§17), one page (§16), every counter (§20). **Read-only: M11 does not build a
single button** — §18's controls are M12's, feature-flag toggles are M13's.

## What each endpoint owns

| Endpoint | Owns | Reads |
|---|---|---|
| `GET /api/debug/events` | the **stream** view: what happened, newest first, with timestamps and delivery state | `outbox_events` ⟕ `processed_events` |
| `GET /api/debug/conflicts` | conflict history: versions, `mutationId`, resolution | `conflict_log` |
| `GET /api/debug/outbox` | the **delivery** view: what is stuck. Outbox rows *and* print jobs — both are at-least-once delivery with attempts, a last error and a dead-letter state | `outbox_events`, `print_jobs` |
| `GET /api/debug/dependencies` | dependency status hard-vs-soft, **consumer lag** (new), outbox backlog | probes + Kafka admin |
| `GET /api/debug/metrics` | every §20 counter, each tagged with its source, plus terminal presence — the two things that are gauges rather than stored records | counters + DB + Redis |

`events` and `outbox` both read `outbox_events` on purpose: one asks *what happened*, the other
asks *what is stuck*. `dependencies` stays in `modules/health` where M6 put it; it is the health
split's third leg (§17) and only gains lag here.

## Where each counter comes from, and why

Three sources, and **the page says which for every number** — a counter that silently resets is
worse than no counter.

| Source | Meaning on screen | Counters |
|---|---|---|
| `process` | in-memory in **this API instance**. Resets on restart, and with several instances it is one instance's share | api requests, api errors, active sockets, mutations received/applied, duplicate mutations prevented, mutation-id reuse rejected, cross-tenant rejections |
| `database` | derived from a row that already exists. Durable, fleet-wide, survives every restart | conflicts detected, blocked mutations, processed mutations, outbox pending/published/dead-lettered, kafka events consumed (per consumer), print jobs pending/printed/failed/dead-lettered |
| `shared` | a Redis counter, because the fact happens in the **worker** and has no row. `null` when Redis is down — which is the point: it is what makes a Redis outage visible | duplicate kafka events prevented |
| `client` | counted in the browser and persisted in Dexie; the server cannot observe it | offline sync successes, offline sync failures |

The rule the brief asks for: **derive from the database wherever the fact already has a row**, and
reach for Redis only for what does not. Exactly one counter needs Redis. `outbox published` and
`print jobs succeeded` are worker facts too, but `outbox_events.published_at` and `print_jobs.state`
already record them, so they stay database-derived and stay honest across a restart.

Two derivations worth naming:

- **kafka events consumed** = `count(processed_events) group by consumer_name`. That is *unique
  events processed*, not *messages delivered*; a redelivery adds no row. Labelled as such.
- **blocked mutations** = `conflict_log where resolution is null` — a conflict nobody has resolved
  is a client queue still halted under §14.1.
- **print jobs failed** is a **gauge**, not a total: it is how many rows sit in `FAILED` right now,
  i.e. attempts BullMQ is still holding a retry for. `PRINTED` and `DEAD_LETTER` are cumulative.

## The three things this turns into a number

From `known-problems.md`, and none of them is fixed here — each becomes visible:

1. **A Redis outage is invisible.** Now: the `redis` dependency row is `down`, the shared counter
   reads `null` with a note, and presence goes empty.
2. **A row can be reclaimed for ever.** `reclaim_count` is a column on every outbox row rendered by
   `/api/debug/outbox`, and a non-zero one is highlighted. The answer was always "a human reading
   /debug"; this is that page.
3. **The kitchen projection is load-bearing for writes (ADR 012).** Consumer lag per group is now
   on the dependency panel, so "the kitchen is behind" is a number rather than a guess.

## Terminal presence

New state with a lifetime, so all three parts are decided up front:

- **Written by** the Socket.IO server, on the `presence` heartbeat and on nothing else — the
  client sends one immediately after `subscribe` on every connect, and then every
  `PRESENCE_HEARTBEAT_MS` (5 s). One writer, not two: `subscribe` carries neither the pending count
  nor the offline switch, so a presence entry derived from it would be a guess at half its fields.
- **Expired by** a Redis TTL of `PRESENCE_TTL_MS` (15 s = three missed heartbeats). A disconnect
  deletes the key eagerly; the TTL is what covers a browser that was killed, a laptop lid, or an
  API instance that died holding the socket. **A presence list that only grows is a bug that looks
  like a feature for ten minutes.**
- **Stale on screen** means `lastSeenAt` older than one heartbeat interval: the entry is still
  inside its TTL but the terminal has missed a beat, so it is marked rather than hidden. Nothing
  else in the system reads presence — it is display only, never a routing decision.

Keys are `presence:terminal:<terminalId>`, one JSON value each, read with `SCAN` + `MGET`.

## Consumer lag

`admin.fetchTopicOffsets(topic)` (high watermark per partition) minus
`admin.fetchOffsets({ groupId, topics })` (committed per partition), summed, for both groups —
`REALTIME_CONSUMER_GROUP` and `KITCHEN_CONSUMER_GROUP`. A partition with no committed offset (`-1`)
counts its whole high watermark as lag. The admin client is injected into `buildApp`, exactly as
the probes are (ADR 006), so an injected test app needs no broker; when it is absent or fails, lag
is `null` with an error string, never a guess.

## The page

`/debug`, polling every 2 s, sections in §16's order: dependencies (hard/soft, latency, impact,
consumer lag, outbox backlog) · active terminals · recent events · conflicts · delivery (outbox
rows with dead-lettered and reclaimed highlighted, then print jobs) · counters grouped by source.
Feature-flag toggles and the failure simulator are named as **M13** and **M12** placeholders, so
the page does not silently omit two of §16's sections.

Badges come from `StateBadge.vue` and §16's required vocabulary: `PENDING`, `DUPLICATE PREVENTED`,
`DEAD-LETTERED`, `CONFLICT`, `BLOCKED`, `ONLINE`, `OFFLINE`.

## Non-goals

No buttons. No `POST /api/debug/flags/:key` (M13). No Prometheus (§20 says optional). No
authentication on `/debug` — it is a demo surface, and the socket has none either
(`known-problems.md`).
