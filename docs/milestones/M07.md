# M7 — IndexedDB persistence

**Model:** Sonnet. **Size:** M. **Previous:** M6 (error model, correlation fields, split health, CI).
**Demoable after:** yes — the same demo as M6, plus the one new thing this milestone is for:
**reload the POS tab and the order is still there**, and a mutation whose answer never came back is
still there too, with the same `mutationId`, still offering Retry.

## Goal

Move the client state that must survive a reload out of memory and into IndexedDB, through Dexie,
in the three tables §14 names: `orders`, `pendingMutations`, `syncMetadata`.

That is the whole milestone. There is no sync engine, no offline toggle and no queue. The tables
are **written** here; they are **read by a sync engine** in M8.

The real work is not the schema — it is that **hydration is a second writer for every piece of
client state that already has an owner**. M4's review rounds found three bugs of exactly one shape:
state that outlives the screen which created it, with no rule about who may write it. M7 adds a
writer that starts before the screen is ready and finishes after it may have moved on. Each
existing rule therefore has to hold across a reload, not merely across a screen:

| Rule | Owner today | What hydration must not do |
|------|-------------|----------------------------|
| `adopt` refuses a snapshot older than the one held | `stores/order.ts` | install a persisted snapshot over a newer one already fetched |
| `adopt` accepts a *different* order unconditionally | `stores/order.ts` | install the persisted order over the one the operator just created |
| `refetch` re-checks that its order is still current | `stores/order.ts` | write after the screen has moved to another order |
| `pendingByTerminal` is keyed by terminal | `stores/order.ts` | resolve one terminal's mutation from another's screen |
| `pendingByOrder` is keyed by order | `stores/kitchen.ts` | restore another restaurant's commands onto this rail |
| `connection.start`/`stop` claim a generation | `stores/connection.ts` | run against a screen that has already been torn down — so the order store claims one too |
| `createCoalescingLoader` runs one read at a time | `realtime/coalescing-loader.ts` | (untouched — the ticket list is server state and is not persisted) |

And the one bug in this milestone that loses money: **a rehydrated pending mutation keeps its
`mutationId`.** That is the entire point of persisting it. Retry sends the same id, §9 answers
`ALREADY_APPLIED`, and the operator learns the truth. A hydration path that mints a fresh id turns
a retry into a second order, and no version check downstream can catch it.

## In scope

1. **The Dexie database** — `apps/web/src/persistence/db.ts`. Schema version 1, three tables,
   only the indexes something already asks for.
2. **A repository over it** — `apps/web/src/persistence/local-store.ts`. Every operation is
   failure-tolerant: IndexedDB can be absent (private browsing) or refuse a write (quota), and
   **neither may ever break a command**. A failed write is recorded in one exported ref and shown
   as a badge; the mutation still goes to the server.
3. **The POS persists on every action**: the canonical snapshot whenever one comes back from the
   server, the pending mutation before it is sent, its deletion **after** that answer is cached,
   its return to `PENDING` when the answer never comes, and the per-terminal pointer saying which
   order this terminal is working on.
4. **The kitchen persists its pending commands**, per order, in the same `pendingMutations` table —
   one row shape for both screens, because M8's sync engine reads one queue.
5. **Hydration at startup**, on both screens, under the guards in the table above, ending in a
   canonical read — the cache is never authoritative, and that refresh must not depend on which
   realtime transport happens to be active.
6. **Pruning.** An order row that no pointer and no pending mutation refers to is deleted at
   hydration. Without it the table grows for the life of the browser profile.
7. **Tests** — `apps/web/test/persistence.test.ts` and hydration cases added to the store tests,
   over a real IndexedDB implementation (`fake-indexeddb`), not a mock of Dexie.
8. **`docs/adr/013-client-persistence.md`.**

## Out of scope

- **The whole of M8.** No `Simulate Offline` toggle, no queue, no sequential sync, no §14.1
  halt-on-conflict, no discard-or-rebase. `PendingMutationStatus` includes `CONFLICT`, `BLOCKED`
  and `SYNCED` because §14 defines the union and both milestones must agree on it; **M7 writes
  only `PENDING` and `SYNCING`**, and a test asserts that.
- **No optimistic UI.** §14 says the UI updates optimistically and never waits for the server;
  that is the same sentence that describes the queue, and it needs the queue to be true. Today the
  screen still shows the server's canonical answer. M8 changes that.
- **No Pinia persistence plugin.** It serialises whole-store state to `localStorage`: not
  IndexedDB, not selective, and not the three tables §14 and M8 need. Recorded in ADR 013.
- No change to any server-side code, to the contracts package, or to the kitchen projection.
- **No re-review of M6.** Five Codex rounds ran and the fifth was clean.

## Decisions this milestone must make before any code

### 1. The snapshot is a cache; the pending mutation is the durable fact

`orders` holds the last canonical snapshot the server gave us. It is **never** authoritative: on
every startup the screen hydrates it and then immediately refetches, and on reconnect §13 refetches
again. Its only job is that a reload with the network down still shows the operator their order.

`pendingMutations` is the opposite. A row there is a fact the server may not know: an intent that
left this device, or one that never left it. Losing it loses money — either an order that was never
placed, or a `mutationId` that can no longer resolve a mutation that *was* applied. This is the
table M8 is built on.

`syncMetadata` is per terminal and holds the pointer — which order this device is working on — plus
when it was last touched. It is keyed by `terminalId` because that is the device, and the device is
what survives a reload. M8 adds fields to it; M7 adds no others.

### 2. Hydration goes through `adopt`, and carries its own owner check

Three rules, and all three are needed:

- it calls `adopt`, so the monotonic-version rule still holds against a refetch that landed first;
- it checks, **after the await**, that the store still holds no order at all;
- and it checks that the screen it was hydrating for is still the screen that is up.

The second is not redundant with the first. `adopt` accepts a snapshot for a *different* order
unconditionally — that is how a `CREATE_ORDER` response installs a new aggregate — so a persisted
order-A snapshot arriving late would silently replace the order-B the operator just created. This
is `refetch`'s guard, restated for a second slow reader. `adopt` cannot tell its callers apart.

The third cannot be the terminal id, which is the obvious choice and the wrong one: the id outlives
the screen. `onBeforeUnmount` clears the order but leaves `activeTerminalId` naming the terminal it
was rendering, so a read still in flight passes an id check and writes into a screen that no longer
exists — or into the next mount of the same terminal. The claim is therefore a **generation**,
bumped by `useTerminal` and by `releaseTerminal`, exactly as `connection.start`/`stop` already do.

### 2a. `adopt` displays; `send` and `refetch` cache

Caching is not a side effect of displaying. The cache is keyed by the terminal that *asked* the
server, and only the caller knows which terminal that was — `send` can answer for a terminal whose
screen has already moved on, and `hydrate` installs a snapshot that came off the disk to begin
with. So `adopt` writes to memory only, and the two callers that obtained a snapshot from the
server persist it themselves.

### 2b. The pending row is deleted after the answer is cached, never before

The two writes are not atomic, and the tab can die between them. Deleting first leaves the one
state in this milestone that loses money: on a `CREATE_ORDER` the row is gone, the snapshot never
arrived, and `createOrder` cleared the pointer before sending — so the reload shows an empty till
and the operator rings the order up a second time. Caching first makes the worst case a row that
outlived its answer, which Retry resolves as `ALREADY_APPLIED`.

### 2c. Hydration ends with a canonical read

Not the view's job. Leaving the refresh to the caller means it happens only where somebody
remembered it, and the obvious place — the socket's `onConnected` — does not run at all when
`realtime.websocket_push` is off or `GET /api/config` fails. `hydrate` therefore restores from disk
and then refetches, so the cache is authoritative for exactly as long as one HTTP round trip.

### 3. A pending slot is filled only if it is empty

Hydration never overwrites a pending mutation created since it started. On the POS the slot is
`pendingByTerminal.get(terminalId)`; in the kitchen it is `pendingByOrder.get(orderId)`. If either
is occupied, the in-memory one wins: it is the more recent intent, and the persisted row will be
reconciled by M8's queue rather than by a startup path.

### 4. The kitchen filters by restaurant, the POS does not need to

A POS pending row carries the `terminalId` that created it, and a terminal belongs to exactly one
restaurant, so reading by terminal is already tenant-safe. The kitchen's rows all carry
`terminalId: 'kitchen-display'` — the same value in every restaurant — so kitchen hydration
**must** filter on `restaurantId` as well. Without it, opening `/kitchen?restaurantId=b` restores
restaurant A's unresolved commands onto B's rail, and retrying one sends a cross-tenant mutation
the server would rightly refuse while the screen insisted it belonged there.

### 5. `SYNCING` is a real state, and finding one at startup is the point

A row is written `SYNCING` **before** the request goes out — §14's ordering, and the state the
mutation is about to be in — deleted when the server answers, and set back to `PENDING` when no
answer arrives. So `PENDING` at rest means an intent nobody is currently attempting, which is what
M8's queue will pick up, and a row still marked `SYNCING` at startup is a request whose tab died
mid-flight. The two are indistinguishable from the client's side and are treated the same: both
hydrate into the pending slot with the `mutationId` intact.

There is deliberately no second write to move a row from `PENDING` to `SYNCING` on the way out.
M7 has no queue, so an intent is formed and attempted in the same breath; M8 introduces the gap
between the two, and with it the durable `PENDING` that precedes a first attempt.

### 6. Persistence failures are reported, never thrown

Every repository call is wrapped: it resolves, records the failure in `persistenceError`, and
returns a neutral value. The ref is **not** cleared by a later success — a failed write is never
retried, so "something this session meant to store is not stored" stays true however well the next
write goes, and the badge is about the device's trustworthiness, not the database's pulse. A browser in private mode with IndexedDB disabled must still be able to
take an order — it just loses durability, and says so on the badge rail. The alternative — letting
a quota error reject inside `send()` — would turn a storage problem into a lost mutation, which is
precisely the failure the storage exists to prevent.

### 7. Vue proxies do not survive `structuredClone`

IndexedDB clones what it stores, and a Vue reactive proxy raises `DataCloneError`. Every value
crossing into Dexie goes through one `plain()` helper (`toRaw`) in the repository, which is the one
place that knows the values came from a store. This is an abstraction against a concrete failure,
not a layer for its own sake.

## Verification

```
pnpm run build:packages
pnpm typecheck && pnpm lint
pnpm -F @pos/web test
pnpm build
pnpm verify:integration
```

- A snapshot cached by an answered mutation and a pending mutation written by `send` are both
  readable from IndexedDB afterwards, and the pending row's `mutationId` is the one that was sent.
- The answer is cached **before** the pending row is deleted, asserted by observing the database at
  the moment of deletion — and cached against the terminal that sent it, not the one on screen.
- Hydration issues a canonical read and adopts a newer server version over the cached one.
- A hydration still reading when the screen unmounts writes nothing, even if the same terminal is
  re-entered before the read lands.
- A store hydrated from those rows offers Retry, and the retry carries **the same `mutationId` and
  the same `baseVersion`** — asserted on the actual request the client made.
- Hydration does **not** overwrite an order created while it was in flight, does **not** overwrite
  an occupied pending slot, and does **not** write at all if the terminal changed under it.
- Hydration installs nothing once the store holds any order — a newer version of the same one or a
  different one alike. The emptiness check is what refuses the different order; `adopt`'s
  monotonic-version rule is the second line of defence behind it.
- Kitchen hydration restores only the commands of the restaurant on screen.
- A server answer deletes the row; a lost answer leaves it `PENDING`; Discard deletes it.
- Every row M7 writes has status `PENDING` or `SYNCING` and no other.
- Pruning deletes an order row nothing refers to and keeps one a pending mutation refers to.
- With IndexedDB made to fail, a mutation is still sent and `persistenceError` is set.
- `pnpm verify:integration` still exits 0 — this milestone touches no server code, and that must
  be visible rather than assumed.

Manual, once, with the user driving Compose: create an order on `/pos/pos-1`, add two items,
**reload the tab** — the order is still on screen. Then stop the API, press Add, reload again — the
unresolved mutation is still there with Retry and Discard, and Retry after the API is back answers
`ALREADY_APPLIED` rather than adding a third item.

## Definition of done

- The three §14 tables exist in IndexedDB through Dexie and are written on every action.
- A page reload does not lose the local order, and does not lose an unresolved mutation's identity.
- Every hydration path is a checked writer: it goes through the existing owner and re-checks its
  claim after every await.
- No `mutationId` is ever regenerated by a hydration path — tested.
- Persistence cannot break a command; a storage failure is visible instead.
- ADR 013 is written, `PROGRESS.md` and `build-log.md` are updated, and the tree is one commit.
