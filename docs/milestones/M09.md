# M9 — Outbox hardening and the crash windows

**Model:** Opus. **Size:** L. **Previous:** M8 (offline queue, sequential sync, halt-on-conflict)
plus its two review rounds. **Demoable after:** partly — pausing the publisher and watching the
outbox fill up is demoable from a terminal, not yet from a screen: §18's buttons are M12's.

## Goal

M3 built the §10 publisher and M6 taught it to survive a broker outage. M9 hardens the two things
neither of them finished: **the lease** — who is allowed to publish a row, and for how long — and
**the crash windows** the design accepts, which are asserted by nothing today. It adds the two
operational switches §18 needs (`Pause Outbox Publisher`, `Delay Outbox Publishing`) as real
controls a running worker honours without a restart, and it writes the three mandatory tests that
cover the windows: §21.12, §21.13, §21.16.

This is the first milestone in three that does not touch `apps/web`.

**Nothing here rebuilds the publisher.** `attempt_count`, `next_attempt_at`, `last_error`,
`dead_lettered_at`, `claimed_by`, `claim_until` and the claim → publish → mark loop all exist and
work. The bounded exponential backoff the milestone list asks for is already in `recordFailure`;
what is missing is everything around the *edges* of a batch.

## The two questions

M8's brief asked "who may write this?" and then "for each pair of writes, which order survives a
crash between them?", and the second question found a regression before the code did. M9 is
*entirely* about crash windows, so both tables come first.

### Question one — who may write this

| State | Who writes it | When | The rule |
|-------|---------------|------|----------|
| `claimed_by`, `claim_until` | the claim step, and only for rows nobody currently holds | one short transaction that commits before any network call | `for update skip locked` keeps two workers out of the same row *during* the claim; the lease keeps them out of it *during* publication |
| `published_at` | the worker that published the record | after the send returns | it is the only writer that knows the send happened. A crash before it is the §21.12 window, not a lost event |
| `attempt_count`, `last_error`, `next_attempt_at`, `dead_lettered_at` | `recordFailure`, once per *failed send of this row* | after a send throws | an attempt means **this event failed**. A broker that died mid-batch, a paused publisher and an expired lease all spend **zero** attempts — otherwise an outage dead-letters events that were never bad (ADR 011) |
| `reclaim_count` | the claim step, when the row it takes was still held by a previous claimant | inside the claim transaction | a reclaim means **a worker died**, not that the event is bad. It is counted so it is visible, and it is deliberately not a dead-letter trigger — see ADR 010 |
| `outbox_controls` | a human, through `pnpm -F @pos/worker outbox …` (M12: through `/debug`) | any time | one singleton row. The publisher only ever reads it |
| the in-memory control snapshot | the control watcher | every `OUTBOX_POLL_MS` | a failed read keeps the **last known** value rather than reverting to the default: a database blip must not silently un-pause a publisher a human paused |
| `processed_events` | each consumer, in the same transaction as its projection | — | unchanged since M3. It is what makes both republication (§21.12) and redelivery (§21.13) survivable |

### Question two — for each pair of writes, which order survives a crash between them

| Pair | The order chosen | What a crash between them leaves | The invariant that makes it safe |
|------|------------------|----------------------------------|----------------------------------|
| the claim **+** the record reaching Redpanda | claim first, committed before the send — §7 forbids a network call inside a transaction | a leased row that was never published | the lease expires and the row is claimable again, with `attempt_count` untouched. This is the only pair whose recovery is *time-based*, and `OUTBOX_LEASE_MS` is therefore a real latency bound |
| the record reaching Redpanda **+** `published_at` | publish first — there is no other order available | an event on the topic whose row still says pending | **§21.12.** The lease expires, the row is republished, and the consumer's `processed_events` row makes the second delivery a no-op. At-least-once is the accepted consequence (§10) |
| the consumer's projection **+** its Kafka offset | projection and `processed_events` commit together, in one transaction, *before* the offset | an event whose projection is done and whose offset says it is not | **§21.13.** Redelivery finds the `processed_events` row and returns `duplicate`. The reverse order — offset first — would lose the projection outright, which is the one failure this design refuses |
| the batch abandoned **+** its claims released | abandon first, then release, in one statement | (a crash before the release) the leases stand until they expire — exactly today's behaviour | the release is a pure optimisation whose failure mode is the status quo, which is why it is safe to add. It is guarded by `claimed_by = :workerId`, so a lease that expired and was re-taken by another worker is never stolen back |
| `attempt_count` **+** clearing the claim | one statement, one row | — | already true in M3's `recordFailure`; named here because the table would otherwise imply a window that does not exist |
| a pause taking effect **+** rows already claimed | the pause is observed *between* rows, and the untouched remainder is released | — | a paused publisher must hold **no** leases: otherwise pausing one worker stalls the other for up to `OUTBOX_LEASE_MS`, which is the opposite of an operational control |
| the lease deadline passing **+** a send already in flight | check the remaining lease *before* each send, counting the delay it is about to incur, **and bound the send itself by what is left** | a record that may still land, late | **the new finding, corrected by review round 1.** A slow broker, a large batch or a non-zero publish delay can push a batch past its own lease; the first version of this guard budgeted only the delay and let the send run unbounded. KafkaJS cannot cancel a send, so what the bound actually buys is narrower than it first claimed: this worker stops publishing — and stops *marking published* — under a claim someone else now holds, and a hung producer stops holding the loop. A late record cannot be a different version out of order, because a successor is unclaimable until its predecessor is published; it can only be a duplicate of an event already on the topic, which `processed_events` absorbs |

## The gap M8 named, and what it turned out to be

`PROGRESS.md` recorded one known gap: *"a batch cut short by the broker dying leaves its untouched
rows leased for up to `OUTBOX_LEASE_MS`."* Fixing it is the fourth row of the table above. Writing
that fix surfaced the seventh row, which is the more interesting one: the abandonment path existed
for a dead transport, but **nothing checked the lease the batch was still running under.** With
`OUTBOX_BATCH_SIZE=50`, `OUTBOX_LEASE_MS=30000` and a broker taking 600 ms a send, the last rows of
a batch publish after the lease has gone. Everything about the outbox assumed that could not happen.

Review round 1 then found that the first fix was half a fix — it bounded the *wait* before a send
and not the send — and that the two operational switches had three problems of their own. Both are
recorded in `build-log.md` under **M9 review round 1**, and the tables above have been corrected
rather than left as they were written.

## In scope

1. **Schema.** `outbox_events.reclaim_count` (integer, not null, default 0) and a new singleton
   `outbox_controls` table (`paused`, `publish_delay_ms`). One generated migration.
2. **`apps/worker/src/modules/events/outbox-controls.ts`** — read, write and watch the singleton.
   The watcher polls, keeps the last good value across a failed read, and logs transitions.
3. **Publisher hardening**, all inside `publishOnce`:
   - release the claims of every abandoned row instead of leaving them to expire;
   - stop the batch when the remaining lease will not cover the next send;
   - honour `paused` between rows, releasing what is left;
   - honour `publish_delay_ms` before each send;
   - count reclaimed rows and report them in `PublishRunResult`.
4. **The worker loop** builds the watcher, skips the claim entirely while paused, and logs it.
5. **`pnpm -F @pos/worker outbox status|pause|resume|delay <ms>`** — the operational switch as a
   command until M12 gives it a button. Not a test hook: the worker reads the same row.
6. **Tests.** §21.12, §21.13 and §21.16 by their spec numbers, plus unit coverage for the release,
   the lease guard, the pause and the delay.
7. **ADR 010** — `010-db-outbox-retries.md`, planned for M9 in `docs/adr/README.md` and referenced
   by §10 of the spec: why retries live in PostgreSQL, and why a reclaim is not an attempt.

### How each test is made honest

- **§21.12 (crash after publish, before `published_at`)** — unit, against PostgreSQL and a fake
  transport. The crash is real, not simulated by editing the row afterwards: the publisher runs
  against a `Db` whose *second* transaction throws, which is exactly the mark step. The row is left
  published-on-the-topic and pending-in-the-table, the lease expires, the next pass republishes it,
  and both deliveries are fed to `applyKitchenEvent` — one `kitchen_tickets` row, one
  `processed_events` row, the second delivery answering `duplicate`.
- **§21.13 (crash after the consumer's commit, before the offset commit)** — integration, and it
  has to be: a redelivery that is not a *real* redelivery proves nothing beyond §21.6, which
  already exists. A consumer runs with `autoCommit: false`, applies the event, and disconnects
  without committing. A second consumer in the same group is then given the same partition, Kafka
  redelivers from the last committed offset, and the projection does not move.
- **§21.16 (lease reclaim, two workers)** — unit, and deterministic without a sleep for the half
  that matters. Worker A's transport blocks on a gate that is opened only after worker B's whole
  pass has finished; because the claim commits before the first send, B provably runs against rows
  A already holds and claims nothing. The reclaim half then uses a short lease and asserts
  `reclaim_count`, so "the lease expired" is observable rather than inferred.

## Out of scope

- `/api/debug/outbox` and the `/debug` page — M11. The dead-letter state is *reachable* after this
  milestone; making it *visible in a browser* is not M9's.
- The eleven §18 buttons — M12. M9 builds two of the switches behind them and no UI.
- Print jobs and BullMQ — M10.
- A consumer-side dead-letter topic. The publish side dead-letters through `outbox_events`; the
  consume side still loses a poison message permanently, and that stays a known problem.
- Archiving `outbox_events` / `processed_mutations`, per-restaurant controls, and any change to the
  claim query's per-aggregate ordering rule.

## Verification

```
pnpm -F @pos/worker test
pnpm -F @pos/api test
pnpm lint
pnpm typecheck
pnpm build
pnpm verify:integration
```

By hand, with Compose up and the worker running:

1. `pnpm -F @pos/worker outbox pause`, then drive an order through the POS. `select count(*) from
   outbox_events where published_at is null` grows, the kitchen screen shows nothing new, and the
   order itself is intact — the API never blocked.
2. `pnpm -F @pos/worker outbox resume`. The backlog drains in version order and the kitchen
   catches up.
3. `pnpm -F @pos/worker outbox delay 3000` and send an order to the kitchen: the ticket appears
   about three seconds late, once per event.
