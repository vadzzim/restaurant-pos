# M18 — Playwright E2E

The §21 browser test, the last line of the testing section: **open POS-1, create an order, add an
item, send it to the kitchen, open the kitchen screen, verify the ticket appears, mark PREPARING,
verify the POS updates.** Wired into CI.

One test, and it is the only test in the repository that proves the *whole* pipeline: browser →
API → outbox → publisher → Kafka → kitchen consumer → projection → WebSocket → the other browser.
Every unit and integration suite so far has cut that chain somewhere.

## Scope

- `playwright.config.ts` at the root, `e2e/` beside it. Chromium only.
- `scripts/verify-e2e.mjs` — the one reproducible command, shaped like `verify-integration.mjs`:
  Compose up, migrate, seed, build, start the three app processes, wait for readiness, run the
  spec, tear down what it started, write everything to `.verify-output/e2e.log`.
- `pnpm test:e2e` runs that script. `pnpm test:e2e:run` runs the spec alone against a stack the
  developer already has up.
- A CI job that runs the same command.

Out of scope: a second browser, a second spec, visual regression, `verify:multi` in CI.

## The decisions this milestone has to get right

### 1. Against the production build, not `pnpm dev`

M17 made the two meaningfully different: the service worker exists only in a production build.
The spec runs against `pnpm -F @pos/web preview` (:4173), which serves `dist/` behind the same
proxy nginx serves in the image. Testing :5173 would test a bundle nobody ships.

Playwright owns that one process through `webServer`, because it already knows how to wait for a
port and how to kill a process tree on Windows. `dist/` must exist first — the verify script
builds it; a bare `pnpm test:e2e:run` against no `dist/` fails loudly in `vite preview`, which is
the right error.

### 2. The API and the worker are Node processes, not Compose services

The `app` profile in `docker-compose.yml` is the *dev* stack: it installs dependencies inside the
container on every start. The verify script builds once and runs `apps/{api,worker}/dist/index.js`
with `node` directly — no shell wrapper, so a kill is a kill on both platforms.

### 3. Poll, never sleep

Send to kitchen returns as soon as the mutation commits. The ticket appears only after the
publisher claims the outbox row, Kafka delivers it and the consumer writes the projection. That is
several hundred milliseconds on a warm machine and several seconds on a cold CI runner, so every
cross-process assertion is a Playwright web-first assertion with its own timeout. No
`waitForTimeout` anywhere in the spec.

The **consumer group join** is not part of that budget and must not be: it can take half a minute,
because a worker killed on Windows never sends `LeaveGroup` and the group carries the previous run's
member until its session expires. The script waits for both groups' assignment — the worker's
`broker connected` and the API's `realtime consumer running` — before the spec starts.

### 4. Preflight: the server-side simulator arms outlive a run

The four §18 controls in `SIMULATOR_CONTROLS` are rows in PostgreSQL (ADR 015). A paused publisher
left over from a demo makes this test fail as if Kafka were broken. `realtime.websocket_push` is
seeded with `onConflictDoNothing`, so a flag turned off by hand stays off through a re-seed. Both
are reset before the spec runs, from the spec's own `beforeAll`, so the guarantee holds for
`test:e2e:run` too and not only for the scripted path.

### 5. A unique cover per run

The database is not reset between runs and the kitchen rail accumulates. The order is opened on a
table number unique to the run, and every locator is scoped to the card carrying it. Product names
are read from the DOM, never hard-coded: a reseed may change the menu, and `BAR_MENU` already
proves the list is data.
