# M5 — All remaining commands and the full conflict matrix

**Model:** Opus. **Size:** L. **Previous:** M4 (vertical slice, frontend).
**Demoable after:** yes — and for the first time the *whole* order lifecycle is demoable:
create → add → change → remove → send → preparing → ready → pay, with cancel available from every
state that permits it, and every refusal explained by a named rule rather than by a version number.

## Goal

M3 built one honest path through the architecture with three mutation types. M4 made it visible.
M5 makes it **complete**: the remaining six mutation types, the whole of §8 in one domain
component, and the two kitchen HTTP adapters of §17.

Nothing about the shape of the write path changes. That was M3's stated contract with this
milestone: `applyMutation` already owns the §7 transaction, `decide()` already owns the question
"may this apply?", and M5 widens both rather than reorganising either.

## In scope

1. **Six new mutation types** — `REMOVE_ITEM`, `CHANGE_QUANTITY`, `PAY`, `CANCEL`,
   `START_PREPARING`, `MARK_READY` — each with its payload contract, its zod branch, its effect,
   and its event.
2. **The complete §8 rule set** in `packages/domain/src/decide.ts`, table-driven and exhaustive
   over (status × mutation type).
3. **The two kitchen HTTP adapters** of §17 — `POST /api/kitchen/orders/:orderId/preparing` and
   `.../ready` — as thin constructors over the same handler.
4. **Payments**, linked to the originating mutation, with the amount taken from canonical server
   state and never from the request.
5. **The kitchen projection advances**: `OrderPreparing`, `OrderReady` and `OrderCancelled` move
   `kitchen_tickets.state`, and the same three event types reach the kitchen room.
6. **The screens**: quantity controls, remove, Pay and Cancel on the POS; three columns and two
   command buttons on the kitchen screen.
7. Tests §21.4, §21.9 and §21.10, plus the full-matrix domain test and the projection advance.

## Out of scope

- No schema change. M2 wrote all thirteen tables; M5 is the milestone that finally uses `payments`
  and the rest of the `kitchen_tickets` state column.
- No offline queue, no rebase UI (M8). A conflict here still means: the server's snapshot replaces
  what the screen held, and the operator retries by hand.
- No `/debug` view of `conflict_log` (M11). The rows are written; nothing renders them yet.
- No print job (M10), no polling transport (M13), no error-model or logging overhaul (M6).

## Decisions this milestone must make before any code

### 1. `SupportedMutationType` disappears

It existed for exactly one reason: to let the type system state that M3 implemented three of the
nine. After this milestone it is `MutationType` with extra steps, and keeping a second name for the
same set invites a future reader to look for the difference. `MUTATION_TYPES` is the one list.

### 2. The order of checks stays: domain rule first, version second

`decide()` still knows nothing about versions, and it still runs before the versioned UPDATE. This
is what §21.4 tests: a client at v5 sends `ADD_ITEM`, the server is at v6 and `CANCELLED`, and the
answer must be `ORDER_CANCELLED` — not `ORDER_VERSION_CONFLICT`. Both are true; only one tells the
operator what to do. If the checks were the other way round the more useful answer would be
unreachable, and a client would rebase onto v6 only to be refused again for the real reason.

### 3. `PAY` carries a method, never an amount

The payload is `{ method }`. The amount written to `payments.amount_cents` is the order's canonical
`total_cents`, read inside the same transaction. A client-supplied amount would be a second source
of truth for money, and reconciling the two would need a rule — "reject a mismatch" — that the
version guard already enforces better: if the total changed, the version changed, and the mutation
conflicts before any of this is reached.

`payments.mutation_id` is unique, so a second payment for one mutation is impossible at the
database level even if every check above it were bypassed. That constraint is a backstop, not the
mechanism: §21.9 passes through `processed_mutations` (§9), like every other repeat.

### 4. Which statuses accept `PAY` is already decided, and stays decided

`ALLOWED_TRANSITIONS` in `packages/domain/src/status.ts` was written in full in M3: `OPEN → PAID`
and `READY → PAID`. So the bar tab is paid at the counter and the table is paid when the food is
ready, while paying an order the kitchen is actively cooking is refused as
`INVALID_STATUS_TRANSITION`. This is a real restaurant taking a real position, it is what the table
already says, and M5 has no reason to reopen it.

### 5. One idempotent-where-safe case, and only one

§8 ends with "a stale operation already reflected in server state: treat as idempotent where
semantically safe". Applied literally everywhere, that bullet would swallow the whole matrix. M5
grants it to exactly two mutations:

- **`REMOVE_ITEM` for an item that is not there** → `ALREADY_APPLIED`. Two terminals removing the
  same burger both wanted the burger gone, and it is gone. Answering `CONFLICT` would halt an
  offline queue (§14.1) over an operation whose intent is satisfied.
- **`CANCEL` on a `CANCELLED` order** → `ALREADY_APPLIED`. Note that §8's `CANCELLED` reject list
  names seven mutation types and `CANCEL` is not among them.

Everything else conflicts, including the tempting ones:

- **`CHANGE_QUANTITY` to the quantity already stored** applies, and bumps the version. §8 says
  concurrent quantity changes to the same item conflict and the server is canonical; it does not
  carve out an exception for two clients that happen to agree. The version guard is what decides
  that race, and adding a value comparison in front of it would mean two different mechanisms
  answering the same question.
- **`START_PREPARING` on a `PREPARING` order** and **`MARK_READY` on a `READY` order** conflict
  with `INVALID_STATUS_TRANSITION`. "Out-of-order transitions conflict" is the rule, and a repeat
  is out of order. A genuine retry of the *same* mutation never reaches this: §9 answers it from
  `processed_mutations` first.

`CHANGE_QUANTITY` naming an item the order does not have is a conflict (`ITEM_NOT_IN_ORDER`), not a
400: the item may have been removed by another terminal a second ago, which is canonical state
disagreeing with the client, not a malformed request.

### 6. The kitchen commands at the version the projection knows

The kitchen screen has no `orders` row. It reads `kitchen_tickets`, and the only version it holds
is `source_event_version` — the order version that produced the event the ticket was built from.
That is a genuine `baseVersion`, because every event that reaches the kitchen room carries the
order version it was written at, and item mutations are forbidden after `SENT_TO_KITCHEN`, so
nothing bumps the order behind the kitchen's back except a command the kitchen room also sees.

The exception is `PAY` from `READY`: it bumps the order and is not a kitchen event, so the ticket
is then one version behind. Nothing valid can follow it — the order is `PAID` and every kitchen
transition is refused — so the stale version costs nothing.

**The consequence is accepted, not hidden:** a kitchen command built on a lagging projection
conflicts, the screen refetches, and the operator presses again. That is the correct behaviour of
an eventually-consistent read model driving a strongly-consistent write, and it is exactly the race
§21.10 tests. Recorded as `docs/adr/012-kitchen-command-base-version.md`.

The kitchen is not one of the four seeded terminals, so its commands carry
`terminalId: 'kitchen-display'` — a constant in `@pos/contracts`. No table has a foreign key to
`terminals`, so this is a label in `processed_mutations` and `conflict_log`, which is all a
terminal id is used for.

### 7. The kitchen screen gets the POS's pending-mutation discipline, per ticket

A kitchen command whose response never came back has the same problem the POS solved in M4: the
`mutationId` is the only thing that can still settle it, and sending another command for that
ticket would throw it away. So the kitchen keeps one unresolved mutation **per order** — the
aggregate, which is the right granularity here and the one M8 generalises to — and that ticket
takes no further command until Retry or Discard. Other tickets keep working.

## Definition of done

- All nine `MUTATION_TYPES` are accepted by the write path, and no type is special-cased outside
  `decide()`, the effect switch and the event-payload switch.
- The two §17 kitchen endpoints exist and construct mutations; they contain no rule of their own.
- A kitchen ticket walks `SENT_TO_KITCHEN → PREPARING → READY` on screen, driven by real mutations.
- `PROGRESS.md`, `build-log.md` and the two ADRs are updated, and the tree is one commit.
