# M19 — Documentation and finale

Size **L**, Opus. **The last milestone.** §23 in full, plus an honest walk of §26.

## Why this one is different

Nothing new is built. Everything §23 asks to explain has already been argued once — in an ADR, in
`build-log.md`, or beside the code. The failure mode here is re-deriving that material and blowing
the budget on prose the repository already contains. **Grep for the argument, then link to it.**
ADRs 001–018 are canon; `docs/adr/README.md` is the real index (`spec.md` §23 lists filenames that
drifted — `006-kafka-at-least-once` is `006-realtime-consumer.md`).

The weaknesses section is not a formality and does not need inventing: `docs/known-problems.md` is
already the honest list — the accepted limits, then twenty-eight P2/P3 entries. The guide's job is
to **choose and frame**, not to generate.

## Deliverables

### 1. `docs/architecture.md`

Three Mermaid diagrams, each with prose that says what the reader should take from it:

- **System diagram** — browser (POS, kitchen, service worker, Dexie) · api · worker · Postgres ·
  Redpanda · Redis, and which arrow is which protocol.
- **Offline-sync sequence** — the §14 engine: one mutation in flight at a time, the canonical order
  replacing the optimistic view, **and the blocked-queue branch** (409 → that order's tail goes
  `BLOCKED`, is never sent, and waits for a discard or a rebase — §14.1, ADR 002).
- **Outbox sequence** — HTTP → transaction → outbox row → commit → worker claim → Kafka → consumer
  → projection → broadcast, with the lock released before the broker call (ADR 005, ADR 010).

Then the **scale section** from §23 — documented, not implemented, and honest about what is
already true in the repo versus what is design: stateless API replicas, pooling, WebSocket scaling
and the Redis adapter, partition count and key selection, hot partitions, Postgres read/write
scaling, tenant partitioning, async workloads, backpressure, consumer lag, rate limits,
observability.

### 2. The pitch, the walkthrough and the answers

- **5-minute pitch** — the architecture in one breath.
- **15-minute walkthrough** — a route through the code: `decide()` → the nine-branch mutation
  endpoint → the outbox → the consumer → the socket → the client's queue. Name files.
- **Demo script** — all ten §19 scenarios: what to click, what to watch on `/debug`, what it
  proves. §18's switches and the two worker CLIs drive most of them.
- **Answers** to every question §23 lists (eighteen of them), each grounded in an ADR or a test.
- **Weaknesses**, chosen from `known-problems.md`. Explicit trade-offs, no pretending.

### 3. `README.md`

Fix the opening — it still claims *"M1 contains only the runnable monorepo"*, wrong for eighteen
milestones. Add the demo sequence and §23's **"Engineering concepts demonstrated"**. Keep the
verify/URL sections; they are current.

### 4. `docs/definition-of-done.md`

§26 walked clause by clause, each with **the test file or command that proves it** — or an honest
"argued, not tested", which is the truthful answer for at least the two concurrency tests that
assert invariants rather than forcing the interleaving (`known-problems.md` already admits this).
Nothing aspirational.

## Constraints

- No source changes are expected. If a §26 clause turns out to be false, that is a P1: fix it, and
  say so in `build-log.md`.
- Do not run `docker compose` by hand (CLAUDE.md rule 3). `verify:integration`, `test:e2e` and
  `verify:multi` own their lifecycles and write `.verify-output/*.log`; read the tail.
- One review pass, P1s only. The backlog is not swept — M19 is already an L. Sweep only what §26
  forces.


Then walk `docs/definition-of-done.md` against the repository and confirm every "proved by" claim
resolves to something that exists. The hand smoke of §19.1 is the user's — the infrastructure is
theirs to start.
