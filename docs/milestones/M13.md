# M13 — Feature flags and the polling fallback

§15 in full: `feature_flags` behind a Redis cache, percentage rollout by a hash of `restaurantId`,
toggling from `/debug` with no restart, and **the polling transport as a complete second
implementation** of §13. Model **Sonnet**, size **M**.

The point of the milestone is the sentence in §15: turning the flag off *degrades latency, it does
not cause an outage*. That is only true if both branches work, so the polling transport is the
larger half of the work and the flag machinery is the smaller.

## What is already there, and what it is missing

- `GET /api/config` (M4) reads `feature_flags` directly: no cache, no rollout, and the client
  fetches it once at bootstrap (`resolveTransport` in `stores/connection.ts`).
- `Transport` has three values, one of which — `PUSH DISABLED` — is a branch with no live updates.
  M13 replaces it with `POLLING`, a transport that works.
- `POST /api/debug/simulator/:control` (M12, ADR 015) is the shape §17's `POST /api/debug/flags/:key`
  must copy: a zod enum on the path segment, a small body, the new state in the response, and a
  sibling `GET` so the page can render without guessing. **Do not invent a third pattern.**
- The presence heartbeat is installed by `connectRealtime`, so a polling client reports none.
  `[M11, P2]`, and this milestone is where it becomes a real defect.

## Resolution rules

`enabled` is the master switch and `rolloutPercent` is who gets it:

```
resolved = enabled && bucket(key, restaurantId) < rolloutPercent
bucket   = fnv1a32(`${key}:${restaurantId}`) % 100
```

The key is in the hash so two flags do not roll out to the same restaurants in the same order.
The seeded buckets are **`demo-restaurant` 1** and **`second-restaurant` 24**, so
`rolloutPercent: 10` is the §19 demo: `POS-1` on `PUSH` and `POS-3` on `POLLING`, side by side.
A test pins both buckets — if the hash ever changes, the demo percentage changes with it.

## The Redis cache

A `FlagCache` port, injected exactly like `PresenceStore` (ADR 006): `buildApp()` without one reads
PostgreSQL every time and every test stays infrastructure-free. Redis is soft — a cache miss, a
timeout or an outage falls through to the table, never to an error.

Short TTL, and **the write deletes the key**, so a toggle is fleet-wide and immediate rather than
"within the TTL" on the instance that did not serve the write.

## The polling transport

`connectPolling` in `apps/web/src/realtime/`, the same shape as `connectRealtime`: it is handed
`refresh` and it calls it on an interval, and it closes. No event gate — there is no event, only a
snapshot, which is what §13 says a reconnect does anyway.

`stores/connection.ts` owns the choice:

- `resolveTransport` returns `PUSH` or `POLLING`; `UNKNOWN` only while `/api/config` is unreachable.
- **Re-poll `/api/config` every 15 s** and rebuild the connection when the value changes. Not a
  reload, and not a socket control event — that is circular when the flag turns the socket off.
- `Force Polling Transport` (§18) now reaches a working transport, so its panel copy and the
  `known-problems.md` entry that apologise for it are both corrected here.

## Presence needs a second path

Presence is what `/debug` uses to show two terminals on two transports, so a polling terminal that
does not report is the demo failing to demonstrate itself.

- Extract the beat out of `socket.ts` into one module both transports use.
- Add `POST /api/presence` — the report the socket sends, over HTTP. It is not in §17's list; say so
  in `known-problems.md` beside `GET /api/kitchen/tickets`.
- `PresenceEntry.socketId` becomes optional and gains `source: 'socket' | 'polling'`, which is what
  makes the transport visible on the terminals panel.

## Deliverables

1. `packages/contracts` — `FlagState`, `FlagsResponse`, `POLLING_INTERVAL_MS`, `CONFIG_POLL_MS`,
   the `PresenceEntry` change, and `flagBucket()` so the API and any test hash the same way.
2. `apps/api/src/modules/config/` — `application/resolve-flags.ts` (rollout + cache + fallback),
   `application/flag-store.ts` (the two table operations), the cache port, and `api/flag-routes.ts`
   (`GET /api/debug/flags`, `POST /api/debug/flags/:key`). `config-routes.ts` loses its stub comment.
3. `apps/api` — `POST /api/presence`, the Redis flag cache in `index.ts`, `FLAG_CACHE_TTL_MS` in
   `packages/config`.
4. `apps/web` — `realtime/polling.ts`, `realtime/presence-beat.ts`, the connection store rewrite,
   the transport badges, a **Feature flags** panel on `/debug` (state, toggle, percentage, and the
   resolved value per seeded restaurant), and the corrected simulator copy.
5. **ADR 008** — why the flag gates the transport and not the write path. The last unwritten ADR.

## Verification

- `pnpm -F @pos/api test` — flag resolution (enabled off, rollout split across the two restaurants,
  cache hit, cache miss falls back to the table, a write invalidates), the flag routes, `/api/config`
  reflecting a toggle without a restart, and `POST /api/presence` landing in the presence store.
- `pnpm -F @pos/web test` — `resolveTransport` picking each branch, the 15 s re-poll switching
  transport on an open client, the polling loop refreshing, the beat firing on both transports, and
  `Force Polling Transport` producing `POLLING`.
- `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm verify:integration`.
- By hand: with `rolloutPercent: 10`, `/pos/pos-1` reads `PUSH` and `/pos/pos-3` reads `POLLING`;
  both stay correct through a mutation; `/debug` lists both terminals with their sources.
