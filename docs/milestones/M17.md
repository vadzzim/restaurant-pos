# M17 — PWA

The app becomes installable and its **shell** survives a cold reload with no network. Nothing else
changes: the offline *data* story is Dexie's and has been since M8 (ADR 013). M17 adds the missing
half — today, offline plus a hard reload is a browser error page, because index.html, the JS and the
CSS come from the network.

**Verification: install the app, go offline, hard reload — the last local order is still on screen
and the queue still drains on reconnect.** If the service worker owns any of that, the milestone
failed: it must serve the shell and get out of the way.

## Scope

1. `public/manifest.webmanifest` + `public/icons/icon-{192,512}.png` and a maskable 512.
   `index.html` links the manifest. Installability is the bar Chrome sets: name, short_name,
   start_url, display `standalone`, theme/background colour, a 192 and a 512 icon.
2. `src/sw/cache-policy.ts` — a **pure** classifier, `classifyRequest({ method, url, mode })` →
   `'shell' | 'asset' | 'menu' | 'passthrough'`. No `fetch`, no `caches`, no DOM: this is the file
   the tests own, and the one that says what may be cached.
3. `src/sw/service-worker.ts` — install/activate/fetch, three strategies, nothing else.
4. `src/pwa/register.ts` — registration, **production builds only**, called from `main.ts`.
5. `vite/service-worker-plugin.ts` — emits `dist/sw.js` from the TS source at build time.
6. `test/cache-policy.test.ts` — every endpoint the app actually calls, asserted `passthrough`.

Out of scope: an update-prompt UI, offline push, background sync, precaching the hashed bundle at
install time (see below), and the twenty-entry backlog.

## The allow-list, and why it is an allow-list

A deny-list is one new endpoint away from silently caching a mutation. So: **everything is
`passthrough` unless it is named.** Named:

- a navigation request → `shell` (network-first, cached `index.html` as the fallback);
- a same-origin `GET` under `/assets/` or one of the static shell paths → `asset` (cache-first;
  Vite content-hashes these, so a hit can never be stale);
- `GET /api/menu` → `menu` (stale-while-revalidate). The one defensible API cache: eleven seeded
  products that change when the seed changes.

Everything else, explicitly: `POST /api/orders/:id/mutations`, `POST /api/kitchen/orders/:id/*`,
**`GET /api/orders/:id`** — a stale snapshot silently replacing the server's truth is the worst
failure this milestone could ship — `/api/debug/*`, `/api/config`, `/api/kitchen/tickets`,
`/api/presence`, and all of `/socket.io/`. Non-`GET` is `passthrough` before anything else is
considered. Cross-origin is `passthrough`.

`passthrough` means the fetch handler **does not call `respondWith` at all** — the request goes to
the network exactly as if no worker were installed, which is also what keeps `/demo`'s and
`/debug`'s 2 s polling honest.

## Decisions to make deliberately

- **No install-time precache manifest.** ~~The shell is cached on first load and on navigation;
  hashed assets are cached as they are fetched. The verification path loads the app before going
  offline, so a runtime cache is sufficient.~~ **Wrong, and Codex caught it:** the load that
  installs the worker fetches the bundle *before* the worker exists, and `clients.claim()` does not
  replay those requests — so a first visit plus an offline reload gets a cached `index.html` whose
  script misses. `install` now precaches the assets the document references, read out of the
  document itself. Still no build-time asset list to rot; see ADR 017.
- **Registration is guarded by `import.meta.env.PROD`,** because dev is Vite on :5173 with HMR over
  a WebSocket and a worker intercepting module requests makes HMR lie. The guard needs a comment
  saying so.
- **Update strategy: `skipWaiting` + `clientsClaim`, and one reload on `controllerchange`.**
  ADR 017. A stale worker showing last week's bundle to an interviewer is worse than no PWA. The
  reload needs a re-entrancy guard or it loops.
- **The SW is built separately** (iife, no imports at runtime), so it is not an ES-module worker
  and needs no `type: 'module'` registration. It gets its own `tsconfig.sw.json` because
  `WebWorker` and `DOM` cannot share one `lib`.
- **Cache versioning:** one cache name per build. `activate` deletes every cache that is not the
  current one, so an update cannot leave a half-old shell behind.

## Verification

```
pnpm -F @pos/web test        # cache-policy.test.ts among them
pnpm lint && pnpm typecheck  # typecheck now covers tsconfig.sw.json too
pnpm -F @pos/web build       # dist/sw.js and dist/manifest.webmanifest exist
```

Then the browser, against a **production** build (`pnpm -F @pos/web build` then a static serve of
`dist/` with the API proxied, or the web image): load `/pos/pos-1`, add an item, confirm the
worker is active and installability is offered, go offline in DevTools, hard reload, and confirm
the order is still on screen. Back online, the queue drains.

One review pass, P1s only.
