# M21 — Verification that can fail

The first of the four grouped sweeps (`MILESTONES.md`, *The second sweep*). It takes the four
backlog entries that live in the **test harness**: both remaining P2s are there, and both have the
same shape — a run that reports PASS while proving less than it claims.

A test that cannot fail is worse than a missing one, because it is counted. That is the whole
argument for doing this group first.

## Scope

Four lines from `docs/known-problems.md`, deleted from it when they are closed.

1. **`[M18, P2]` `pnpm test:e2e` reuses a foreign API.** `verify-e2e.mjs` probes `:3000` for two
   seconds and, if something answers, runs the whole spec against it — so an edited route handler
   with the old API still up reports PASS. The bundle is always this run's and the worker is always
   fresh; the API process is the entire gap.
   **Fix:** stop reusing by default. A port that is already occupied ends the run with an
   instruction, and `--reuse-api` keeps the escape hatch — explicit, named in the summary line and
   in the log, which is the difference between a documented reuse and a silent false PASS.
2. **`[M14, P2]` `verify:multi` writes to the demo database.** It migrates, seeds and runs the
   §19.10 assertion against `pos`, so every smoke run leaves two throwaway orders on table 19 in
   `demo-restaurant` and a demo opened afterwards shows them.
   **Fix:** its own database, created if absent, named by one constant and passed to the replicas
   through the overlay. `TEST_DATABASE_URL` already establishes the convention (`packages/config`:
   *tests own their own database so a test run never truncates the demo the user has on screen*) —
   this is the one runner that never got it.
3. **`[M18, P3]` `test:e2e` terminates its worker.** `child.kill()` on Windows is a terminate: no
   shutdown runs, no `LeaveGroup` is sent, and the `kitchen` group holds a dead member until its
   session expires — so the *next* run waits out a rebalance, which is why `GROUP_JOIN_TIMEOUT_MS`
   is 120 s.
   **Fix:** the shutdown channel the entry says is missing. Both processes read a `shutdown` line
   on stdin when `STDIN_SHUTDOWN` is set and run the same `shutdown()` a signal runs; the runner
   writes it, waits, and keeps the existing kill as the fallback. Off by default, so a `pnpm dev`
   on a TTY is untouched. The API gets it too: it holds a place in the `realtime` group exactly as
   the worker does in `kitchen`, and since fix 1 it is no longer usually a process this run reused.
4. **`[M18, P3]` the spec asserts no money.** Both totals are on screen and ignored, so a server
   that accepted every mutation and computed `totalCents` wrongly would pass.
   **Fix:** read the tile's price from the DOM, order two of that product, and assert the order
   total *and* the kitchen ticket's total against `2 × price`. Read rather than hard-coded, for the
   reason the spec already gives about product names: the menu is seed data.

## Out of scope, and why

- The other thirteen backlog entries. They are M22, M23 and M24, grouped by surface.
- The preview server's own reuse (`reuseExistingServer: !isCI`). Vite `preview` serves `dist/` from
  disk, so a reused one still serves this run's build — the failure mode the P2 describes does not
  exist there. What a reused preview *can* carry is a stale proxy target, which fix 1 turns into a
  loud failure rather than a quiet wrong answer.
- Making `verify:multi` reset its database between runs. A dedicated database that accumulates is
  already the whole of the complaint; truncation is a second decision with no line asking for it.

## Files

- `scripts/verify-e2e.mjs` — the reuse decision, `--reuse-api`, the worker's graceful stop.
- `scripts/lib/compose-run.mjs` — `startService({ shutdownCommand })`, used by `stop()`.
- `scripts/verify-multi-instance.mjs` — the dedicated database, and creating it.
- `docker-compose.multi.yml` — `DATABASE_URL` for the three services becomes interpolatable.
- `apps/worker/src/index.ts`, `apps/api/src/index.ts`, `packages/config/src/index.ts`,
  `.env.example` — the stdin control and its flag.
- `e2e/kitchen-flow.spec.ts` — the money assertions.
- `docs/known-problems.md` — four lines deleted. `docs/build-log.md`, `docs/PROGRESS.md`.

## Key decisions

- **The escape hatch stays, and is named.** `--reuse-api` is how the user with a demo stack up runs
  the spec without stopping it; the summary line then says the run proved nothing about the API it
  built, exactly as the reuse branch does today.
- **The stdin channel is opt-in and is not a control plane.** One command, one word, no arguments.
  §18's switches live in PostgreSQL and on `/debug` (ADR 015) and none of them moves here.
- **The multi-instance database is `pos_multi`, not `pos_test`.** The integration suite truncates
  `pos_test` between tests; this stack's replicas are containers that would be running against it
  at the same time.

## Verification

- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`.
- `pnpm test:e2e` green from a clean state, and — the point of fix 1 — **failing with the new
  message** when an API is left on `:3000`, rather than passing.
- `pnpm test:e2e` twice in a row: the second run's `Consumer has joined the group` duration does
  not escalate (fix 3), and `.verify-output/e2e.log` shows the worker stopping rather than exiting.
- `pnpm verify:multi` twice: PASS both times, and `demo-restaurant` in the **demo** database holds
  no new orders afterwards (fix 2).
- The spec fails when the server's arithmetic is wrong — one cent added to `recalculateTotal`
  (fix 4). **Not** when a seeded price changes: the price is read off the same screen as the total,
  so both move together and the assertion is about what lies between them.

## Definition of done

The four lines are gone from `docs/known-problems.md`, the commands above are green, and each fix
has something that fails without it — the E2E money assertions and the two-run rebalance for the
spec, and for the two script fixes the log line that names the new behaviour.
