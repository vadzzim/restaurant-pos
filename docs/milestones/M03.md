# M3 — Vertical slice, backend

**Model:** Opus. **Size:** L. **Previous:** M2 (schema, migrations, seed).
**Demoable after:** no — M4 adds the screens. This milestone makes the whole spine work:
HTTP → transaction → outbox → Redpanda → consumer → projection.

## Goal

The narrowest honest path through the entire architecture, for three mutation types only:
`CREATE_ORDER`, `ADD_ITEM`, `SEND_TO_KITCHEN`. Everything on that path is finished, not sketched:
the §7 transaction in full, the §10 three-step lease, a real `kitchen_tickets` projection with
§12.1 idempotency, and the seven tests §21.1, 21.2, 21.3, 21.5, 21.6, 21.11, 21.15.

M5 adds the remaining six mutation types by extending the domain rules. It must not need to
reshape the handler.

## Structural change this milestone forces

M2 put the schema in `apps/api/src/db`. The outbox publisher and the kitchen consumer run in
`apps/worker` (§1) and need exactly the same tables, and one workspace cannot import another
app's source. So the persistence layer moves to a new workspace package:

```
packages/db/  src/{schema,client,testing}.ts  scripts/{migrate,seed,check}.ts  drizzle/  drizzle.config.ts
```

`apps/api` and `apps/worker` both depend on `@pos/db`. The migration files move unchanged — the
database is not touched, only the file that defines it. Root scripts `db:generate db:migrate
db:seed db:check` now proxy to `@pos/db` instead of `@pos/api`.

This is a correction to M2's placement, not a new decision about persistence: ADR 007 still holds.

## In scope

### 1. `packages/contracts` — the shared vocabulary

- `EVENT_TYPES` and `EventType`: for this slice `OrderCreated`, `OrderItemAdded`,
  `OrderSentToKitchen`; the remaining six names from §11 are declared now so M5 only writes
  emitters.
- Payload types for those three events, and `OrderSnapshot` / `OrderItemSnapshot` DTOs.
- `MutationRequest` and the four response shapes from §5 (`APPLIED`, `ALREADY_APPLIED`,
  `CONFLICT`, `MUTATION_ID_REUSED`, plus the `REJECTED` rejection), so M4's Vue client shares the
  exact types the API returns.
- `ConflictReason`: `ORDER_VERSION_CONFLICT`, `ORDER_CANCELLED`, `ORDER_ALREADY_PAID`,
  `ORDER_ALREADY_SENT_TO_KITCHEN`, `ORDER_ALREADY_EXISTS`, `INVALID_STATUS_TRANSITION`.

### 2. `packages/domain` — the rules, with no database and no HTTP

- `calculateTotalCents(items)` — integer cents only.
- `isValidTransition(from, to)` for the full §3 status set, so M5 inherits it.
- `decide(state, command)`: the single place that answers "may this mutation apply to this order
  as it stands?" It returns either an `apply` decision carrying the resulting status and the item
  change, or a `conflict` decision carrying a `ConflictReason`. It knows nothing about versions —
  that guard is SQL (§6) — except that it is called after the tenant check and before the
  versioned UPDATE.
- The rules this slice needs: `ADD_ITEM` and `SEND_TO_KITCHEN` are rejected on a `CANCELLED` or
  `PAID` order; `ADD_ITEM` is rejected once the order is `SENT_TO_KITCHEN` or beyond (§8 — the
  kitchen is already cooking, and this is the rule the whole offline conflict demo depends on);
  `SEND_TO_KITCHEN` requires `OPEN`.
- Unit-testable and unit-tested. Everything else in this milestone needs PostgreSQL; this does
  not.

### 3. `apps/api` — one write path

`POST /api/orders/:orderId/mutations` and nothing else. No `POST /api/orders` (§17), no kitchen
adapters yet (M5), no `GET /api/orders/:id` — M4 introduces reads when a screen needs them.

- **Boundary validation is zod** (`mutationId` uuid, `terminalId`, `restaurantId`,
  `baseVersion` int ≥ 0, `type` from the three supported values, `payload` per type). A rejected
  body is `400 VALIDATION_FAILED` in the §17 error shape.
- `requestHash(orderId, type, payload)` — sha256 over a canonical JSON serialization with sorted
  object keys, so key order in the client's JSON cannot produce a false `MUTATION_ID_REUSED`.
- **The handler, one transaction, in §7's order:**
  1. read the order row; if it exists and its `restaurant_id` differs from the request's →
     `403 CROSS_TENANT_MUTATION`, before any version check and before any write;
  2. look up `processed_mutations` by `mutation_id`; a hit with a different `request_hash` is
     `409 MUTATION_ID_REUSED` and the cached result is *not* returned; a hit with the same hash
     returns the stored `result_json` as `ALREADY_APPLIED`;
  3. domain decision against the current state (`decide`) — a domain conflict wins over a version
     conflict, which is what §21.4 will assert in M5;
  4. the versioned UPDATE from §6, `WHERE id = $1 AND version = $2`; zero rows affected is
     `ORDER_VERSION_CONFLICT` even though step 3 read a matching version, because the read is not
     the guard;
  5. the item change, then `total_cents` recomputed from `order_items` inside the same
     transaction;
  6. `INSERT processed_mutations`;
  7. `INSERT outbox_events` — the event the publisher will pick up.
- `CREATE_ORDER` takes the same path with `baseVersion: 0` and an `INSERT` in place of the
  versioned UPDATE. A duplicate primary key means the order already exists: identical content
  returns that order (§21.15), different content is `ORDER_ALREADY_EXISTS`.
- A unique-violation on `processed_mutations.mutation_id` means a concurrent duplicate of the same
  mutation won the race — the transaction rolls back and the handler returns `ALREADY_APPLIED`
  from the row the winner wrote. Two racing retries must not produce two items.
- Every conflict is written to `conflict_log` in a **separate short transaction** after the
  mutation transaction has rolled back (§8). A cross-tenant rejection writes nothing at all —
  §21.11 requires no state change, and it is a rejection, not a domain conflict.
- Responses follow §5 exactly (`status`/`reason`/`serverVersion`/`canonicalOrder`); other failures
  use the §17 `{ code, message, details }` shape. No stack traces in responses.
- pino logs carry `requestId mutationId orderId restaurantId terminalId` (§20). Counters are M6.

### 4. `apps/worker` — publisher and consumer

- **Outbox publisher, §10, three steps, no broker call inside a transaction:** claim a batch by
  lease (`claimed_by`, `claim_until`, `FOR UPDATE SKIP LOCKED`) and commit; publish to Redpanda
  outside any transaction; mark `published_at` in a second short transaction. On failure:
  `attempt_count + 1`, `last_error`, `next_attempt_at` with bounded exponential backoff, and
  dead-lettering past the attempt ceiling. Publication is at-least-once and says so in the code.
- Topic `restaurant.order.events`, **message key = `orderId`**, so a single order's events keep
  their order within one partition (§11). The worker ensures the topic exists at startup rather
  than relying on broker auto-creation.
- **Kitchen consumer, §12.1:** for every message, one transaction — `INSERT processed_events
  (event_id, 'kitchen') ON CONFLICT DO NOTHING`; no inserted row means a duplicate, skip; then
  upsert `kitchen_tickets`, guarded by `source_event_version` so a redelivered older event cannot
  move the projection backwards. `OrderSentToKitchen` creates or refreshes a ticket; other event
  types are recorded as processed and change no projection row. That is honest for this slice —
  the kitchen has nothing to display before an order is sent.
- Both loops shut down cleanly on SIGTERM, alongside the existing heartbeat.

### 5. Tests — Vitest against a real PostgreSQL

- **Test database:** `TEST_DATABASE_URL`, default `postgresql://pos:pos@localhost:5432/pos_test`.
  A global setup creates that database if it is missing, runs the migrations and seeds reference
  data; each test truncates the transactional tables. The demo database keeps its state — the user
  runs Compose continuously and a test run must not wipe what is on their screen.
- `packages/db/src/testing.ts` exports that setup so both app test suites use one implementation.
- `apps/api` (`pnpm -F @pos/api test`):
  - §21.1 two concurrent `ADD_ITEM` at the same `baseVersion` → one `APPLIED`, one `CONFLICT`.
  - §21.2 the same mutation twice → one item, one outbox row, `ALREADY_APPLIED` second.
  - §21.3 the same `mutationId` with a different payload → `409 MUTATION_ID_REUSED`, the first
    effect untouched, no second outbox row.
  - §21.5 outbox atomicity: applied → order change **and** event; conflicted → neither.
  - §21.11 cross-tenant → `403`, order unchanged, zero outbox rows — asserted through the route
    with `fastify.inject`, so the status code is real.
  - §21.15 `CREATE_ORDER` idempotency, all three cases from §5.
- `apps/worker` (`pnpm -F @pos/worker test`):
  - §21.6 the same event consumed twice → one `kitchen_tickets` row at one
    `source_event_version`, one `processed_events` row.
  - a redelivered lower-version event leaves the projection unchanged.
- Kafka is **not** in the test path. The publisher is tested at the claim/mark boundary with a
  fake transport; the real broker round trip is verified by hand at the end of this milestone and
  automated in M6 by `pnpm verify:integration`. §21.12 and §21.16 belong to M9.

## Decisions to record as ADRs

- `docs/adr/003-optimistic-concurrency.md` — the versioned UPDATE, why a read-then-write check is
  not a guard, and why generic last-write-wins is rejected.
- `docs/adr/004-idempotency.md` — `mutationId` plus `request_hash`, and why a reused id with a
  different payload must never return the cached result.
- `docs/adr/009-kitchen-projection.md` — why the kitchen consumer needs a real read model for its
  idempotency to be demonstrable rather than asserted.

## Verification

Claude runs, against the PostgreSQL the user already has up:

```bash
pnpm typecheck
pnpm lint
pnpm build
pnpm -F @pos/domain test
pnpm -F @pos/api test
pnpm -F @pos/worker test
```

All green, and the seven mandatory tests are present by name.

The user then confirms the real round trip, with `pnpm dev` running:

```bash
curl -s -X POST localhost:3000/api/orders/11111111-1111-4111-8111-111111111111/mutations -H 'content-type: application/json' -d '{"mutationId":"22222222-2222-4222-8222-222222222222","terminalId":"pos-1","restaurantId":"demo-restaurant","baseVersion":0,"type":"CREATE_ORDER","payload":{"tableNumber":"12"}}'
```

then `ADD_ITEM` at `baseVersion: 1` and `SEND_TO_KITCHEN` at `baseVersion: 2` against the same
order, and finally:

```bash
pnpm db:check
```

Expected: three `outbox_events` rows all with `published_at` set, three `processed_events` rows,
and exactly one `kitchen_tickets` row. The Redpanda console at `http://localhost:8080` shows the
three messages on `restaurant.order.events` under the same key.
