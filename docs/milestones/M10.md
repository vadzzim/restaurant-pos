# M10 — The BullMQ print job

**Model:** Sonnet. **Size:** M. **Previous:** M9 (outbox lease, the crash windows, the two §18
publisher switches) plus its review round. **Demoable after:** yes — §19.9 end to end from a
terminal: the printer is failed, the job retries with backoff, it dead-letters, the printer
recovers, a manual retry succeeds, and the order was never affected.

## Goal

Printing a kitchen ticket is the one effect in this system that leaves the database and lands on a
device. It cannot join a transaction, it needs its own retry policy and its own visible dead-letter
state, and it is therefore **the one place BullMQ belongs** (§12.3). Everything else about retries
stays where ADR 010 put it.

The milestone builds five things: a fake printer endpoint that honours an idempotency key and can
be failed on demand, a BullMQ queue and worker, `print_jobs` as the durable record keyed by
`ticket_hash`, a reconciliation sweep that repairs every way the enqueue can be lost, and the
honest statement — in the UI, in the docs and in the code — that **this is at-least-once and a
duplicate ticket can physically print**.

**This milestone is first on the drop list** (`MILESTONES.md`), and it is being built rather than
cut. Worth knowing why it earns its place: it is the only component in the repository where the job
and the record it describes are allowed to disagree, and the sweep is what makes that safe.
Contrasting it with the outbox — where they are forbidden to disagree, which is exactly ADR 010 —
is the interview point.

## The two questions

### Question one — who may write this

| State | Who writes it | When | The rule |
|-------|---------------|------|----------|
| `kitchen_tickets` | the kitchen consumer's projection transaction | before anything is enqueued | unchanged since M3. It is the **source of truth for what should have printed**, which is what makes the sweep possible at all |
| the BullMQ job | the kitchen consumer, *after* its transaction commits, and the sweep | outside every transaction — §7 forbids the network call inside one | the enqueue is best effort. A failure to enqueue is logged and **never fails the message handler**: throwing there would leave the offset uncommitted and redeliver an event whose projection is already applied, for ever |
| the `print_jobs` row | the **processor**, never the enqueuer | on the first attempt of a job | this is the load-bearing choice of the milestone. "A ticket with no `print_jobs` row" then means "nothing has ever tried to print this", which is precisely what the sweep looks for. A row written at enqueue time would make a lost job indistinguishable from an in-flight one |
| `attempt_count`, `last_error`, `state` | the processor, once per attempt | around the HTTP call | an attempt means **this ticket failed to print**. There is no pause and no lease to charge here, so the rule is simpler than ADR 010's |
| `state = 'DEAD_LETTER'` | the processor, on the attempt that exhausts `PRINT_MAX_ATTEMPTS` | — | terminal. Neither the sweep nor a redelivery may revive it; only a human, through `printer retry` (M12: a button) |
| `printer_controls` | a human, through `pnpm -F @pos/worker printer fail` / `fix` (M12: through `/debug`) | any time | one singleton row, the same shape M9 gave `outbox_controls`, and for the same reason: the process that flips the switch is not the process that obeys it, and a switch thrown mid-demo must survive a restart |
| the printer's idempotency ledger | the fake device, in its own memory | per accepted print | **deliberately not in the database.** A real printer's dedup window is its own memory and it forgets on a power cycle; modelling it as a durable table would be the one place this milestone claimed a guarantee it does not have |

### Question two — for each pair of writes, which order survives a crash between them

| Pair | The order chosen | What a crash between them leaves | The invariant that makes it safe |
|------|------------------|----------------------------------|----------------------------------|
| the projection **+** the enqueue | projection first, committed, then enqueue — §7 | a kitchen ticket that no job will ever print | **this is why the sweep exists.** The ticket has no `print_jobs` row, the next sweep finds it and enqueues it. The reverse order would print tickets for projections that never committed |
| the enqueue **+** the offset commit | the enqueue is not part of the offset decision at all | a redelivered event whose projection answers `duplicate` and which therefore enqueues **nothing** | the redelivery path (§21.13) deliberately does not re-enqueue: it cannot tell whether the first delivery got as far as the enqueue. The sweep is the single repair for both windows, which is one mechanism instead of two |
| the paper **+** `state = 'PRINTED'` | print first — there is no other order available | a ticket that physically emerged and a row that says it did not | **§12.3, stated plainly.** The retry prints it again. `ticket_hash` deduplicates the *record*, the `Idempotency-Key` deduplicates what the *endpoint* accepts within its memory, and neither can promise anything about paper |
| the `print_jobs` insert **+** the HTTP call | insert first, in its own short transaction | a `PENDING` row nobody is working on | BullMQ's stalled-job recovery re-runs it while Redis holds the job; if Redis lost the job, the sweep re-enqueues rows left `PENDING` or `FAILED` past `PRINT_STALE_MS`. `PRINTED` and `DEAD_LETTER` are never swept |
| a dead letter **+** a manual retry | reset `state` and `attempt_count` in the database first, then enqueue | a reset row with no job | the next sweep re-enqueues it: a reset row is `PENDING` and immediately stale. The reverse order would enqueue a job the processor refuses — it would still read `DEAD_LETTER` — and the retry would look like it had worked while nothing printed. The `add` always lands because no terminal job is ever retained under the ticket's id |

## Redis, and whether readiness changes

**No.** Redis stays a soft dependency and `/api/health/ready` keeps checking PostgreSQL only
(ADR 011). A Redis outage means tickets are not printed *yet* — orders are still accepted, still
projected, and every unprinted ticket is still sitting in `kitchen_tickets` waiting for the sweep,
because the sweep's input is the projection and not the queue. Marking the API unready would take a
working POS offline to protect a printer, which is the exact inversion the architecture exists to
prevent. Recorded in ADR 014.

## In scope

1. **Schema.** `print_jobs` already exists (M2) with `ticket_hash` unique, `attempt_count`,
   `last_error` and `state`. It gains `restaurant_id`, `printed_at` and an index on `state`; a new
   singleton `printer_controls` table (`failing`) joins `outbox_controls`. One generated migration.
2. **`ticket-hash.ts`** — a stable hash over `{orderId, tableNumber, items}`, computed identically
   from the `OrderSentToKitchen` payload and from a `kitchen_tickets` row, because the live path
   uses the first and the sweep uses the second and they must agree.
3. **The fake printer** — `POST /api/printer/print` in the API, taking an `Idempotency-Key` header.
   It answers `printed: false` for a key it has already accepted, and `503 PRINTER_OFFLINE` while
   `printer_controls.failing` is set. Its ledger is a bounded in-memory map.
4. **The queue and the processor** — a BullMQ `Queue` and `Worker` in `apps/worker`, `jobId` set to
   the ticket hash so a live duplicate is dropped by the queue itself, `attempts` and exponential
   `backoff` from configuration, `removeOnComplete` and `removeOnFail` both on: the visible record
   is `print_jobs`, not BullMQ's failed set, and a terminal job left under the ticket's id would
   silently swallow every later `add` for it.
5. **The kitchen consumer** enqueues after its transaction commits, only for an `OrderSentToKitchen`
   that actually `applied`, and only logs when the enqueue fails.
6. **The sweep** — every `PRINT_RECONCILE_MS`, enqueue every ticket with no `print_jobs` row and
   every row left `PENDING` or `FAILED` past `PRINT_STALE_MS`.
7. **`pnpm -F @pos/worker printer status|fail|fix|retry <orderId>`** — §18's `Fail Printer` and
   §19.9's manual retry as commands, until M12 gives them buttons.
8. **The honesty, in the UI** — the kitchen screen says that tickets print at-least-once and a
   duplicate can physically print. One line, and it is the point of the milestone.
9. **ADR 014** — why BullMQ is right here and wrong for the outbox, why the record is written by
   the processor, and why Redis stays soft.

### How each test is made honest

- **§21.14 (print job deduplication)** — an API test against the endpoint, because that is what the
  spec says it tests: the same `Idempotency-Key` posted twice, one physical print, the second
  answering `duplicate`. A different key for the same order prints again — which is the property
  that makes the first assertion mean something.
- **The processor** — against PostgreSQL with a fake printer that can be told to fail. A success
  writes `PRINTED` and `printed_at`; a failure increments `attempt_count` and rethrows so BullMQ
  retries; the attempt that reaches `PRINT_MAX_ATTEMPTS` writes `DEAD_LETTER`; a job replayed
  against a `PRINTED` row prints nothing; a job replayed against a `DEAD_LETTER` row prints nothing.
- **The sweep** — against PostgreSQL with a fake queue, asserting all four cases of the table above
  rather than only the happy one.
- **The round trip** — a new integration test under `pnpm verify:integration`: a real Redis, a real
  BullMQ worker, the same ticket enqueued twice, one print. Without it the only proof that the
  BullMQ wiring works would be that it compiles.

## Out of scope

- `/api/debug/print-jobs`, the §20 print counters and the `/debug` page — M11.
- The eleven §18 buttons — M12. M10 builds `Fail Printer` as a switch and no UI.
- Any change to the outbox's retry mechanism. ADR 010 is accepted; the contrast is the point.
- A real printer, a print preview, or ticket layout. The device is a fake and the body is JSON.
- Per-restaurant printers. One fake device, fleet-wide, like `outbox_controls`.

Scenario §19.9 by hand, with Compose up, the API and the worker running:

1. `pnpm -F @pos/worker printer fail`.
2. Drive an order to the kitchen from the POS. The ticket appears on the kitchen screen — the order
   is unaffected — and the worker logs a failed print attempt, then another, spaced by the backoff.
3. `select state, attempt_count, last_error from print_jobs` reaches `DEAD_LETTER`.
4. `pnpm -F @pos/worker printer fix`, then `pnpm -F @pos/worker printer retry <orderId>`. The row
   reaches `PRINTED` and the API logs one accepted print.
