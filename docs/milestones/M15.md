## The finding this milestone is built on

`PosView.run()` sets one `busy` flag around every action, and every action ends in
`orders.enqueue()` → `await sync()` → a network round trip. So **every menu tile and every ± button
on the screen is disabled until the server answers a tap on any one of them.** Offline that is
invisible (the client rejects instantly); online with the M12 latency simulator armed it locks the
till out for the whole round trip, on every tap.

The optimism §14 asks for is already in the store: `enqueue()` writes the queue row and calls
`refreshQueue()` *before* it syncs, and `projected` is a pure function of cache + queue, so the
screen is already correct one microtask after the tap. `sync/engine.ts:289` already coalesces —
a trigger arriving mid-pass joins the running pass and makes it loop again — so rapid taps are
safe by construction. **The store was never the thing that waited. The view was.**

## Scope

1. **The critical path stops awaiting the network.**
   Item taps (add, ±, remove) await the local durable write and nothing else; the sync is fired,
   not awaited. Rejections route to `orders.lastError` — no bare floating promise.
   *Commit* actions keep blocking: create, send to kitchen, pay, cancel, discard, rebase. A
   double-fired `PAY` is worse than a lag, and each is one tap the operator then looks up from.
   So: two flags, `committing` and nothing on the item path — not one `busy`.

2. **Menu tiles become the quantity control.** `ADD_ITEM` merges into the existing line in both
   `decide()` and `domain/project-queue.ts`, so tapping a tile twice already means two. The tile
   just never said so: give it a live count badge from `shown.items`. That is §16's "quantity
   reachable in one tap", and it is transport-agnostic because it reads the projection.

3. **Large touch targets.** Menu tiles and the ± steppers to ≥ 56 px; the current ± are 32 px.
   Order lines, action buttons and the terminal switcher sized to be hit without aiming. The
   aesthetic stays the neutral one §16 asks for — no visual investment beyond size and contrast.

4. **No keyboard on the critical path.** Creating an order currently requires typing into a text
   input. Add a one-tap pad of tables (bar: tabs); keep the free input beside it for anything else.
   Still no modal anywhere — the codebase has none today and ends with none.

5. **The conflict banner leads with the two actions.** Today the halted panel is ~40 lines of
   correct prose above the Discard/Rebase buttons. Invert it: one line of what happened, the two
   large buttons, and the evidence (canonical vs. queued intent, the §14.1 cascade argument, the
   rebase semantics) kept in full inside a `<details>`. Nothing is deleted — §16 wants technical
   state obvious — it stops being in the way.

6. **BAR-1 wired up.**
   - **A terminal switcher.** The real gap: nothing in the UI links anywhere but `/pos/pos-1`.
     All four terminals one tap away, on the POS screen, showing which is current.
   - **A bar profile.** `TerminalDescriptor` gains `profile: 'dining' | 'bar'`; `BAR_MENU` (a set of
     product ids) sits beside `TERMINALS` in `packages/contracts`, for the reason already written
     there — both sides need it. The client filters the menu it already fetches.
     **Why not a `category` column on `products`:** it would be a migration + contract + API + seed
     change inside a presentation milestone, and CLAUDE.md forbids an abstraction without a
     concrete problem. Record the tradeoff in `PROGRESS.md`; do not open a backlog entry for it.
   - **Drinks in the seed.** The seed has two drinks, so a filtered bar screen would be two tiles.
     Add four to `packages/db/src/reference-data.ts` — an upsert, no migration. Re-seed after.
   - BAR-1 must be visually unmistakable beside POS-1 in a second window: §19 is demoed with two
     windows side by side and a screenshot must not need a caption.

7. **Pure logic into `apps/web/src/domain/pos-screen.ts`, with tests**, matching
   `debug-view.ts` / `project-queue.ts`. What belongs there: the per-product tile state (count,
   enabled) from the projection, the conflict banner's summary line from `currentConflict` +
   `currentQueue`, the menu filter for a profile. The view renders it and holds no rules.
   `apps/web` has 153 tests and they are the regression net; the count moves up.
