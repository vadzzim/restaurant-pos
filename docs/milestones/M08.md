# M8 — Offline queue, sequential sync, halt-on-conflict

**Model:** Opus. **Size:** L. **Previous:** M7 (IndexedDB persistence) plus its two review rounds.
**Demoable after:** yes — §19.2 and §19.3 by hand. POS-1 goes offline, keeps working, builds a
queue, comes back and drains it in order; and when another terminal has moved the order underneath
it, the queue **stops** and asks a human.

## Goal

Turn the durable tables M7 built into the §14 client: every action becomes a queued mutation, the
screen shows the result immediately without waiting for the server, and a background engine drains
the queue **one mutation at a time per aggregate**. When the server answers `409`, §14.1 applies in
full: that mutation is `CONFLICT`, every later mutation for the same order is `BLOCKED` and never
sent, mutations for other orders keep syncing, and nothing resolves itself.

M7's slot becomes a queue. That is the milestone in one sentence, and it changes three things that
were previously true by accident:

- **the POS gets per-order granularity.** The kitchen has had it since M5 (`pendingByOrder`); the
  POS has had one slot per *terminal*, which is coarser than the aggregate §14.1 halts at. A queue
  keyed per order is not a refactor to skip — §21.8 asks for exactly the behaviour the terminal
  slot cannot express: one order halted while another keeps syncing;
- **retry stops being a button.** A mutation whose answer never came is simply still in the queue,
  and the next trigger re-sends it with the same `mutationId`. `identityFor`/`sameMutation` — M7's
  way of finding the id to reuse — are deleted, because the row *is* the identity;
- **the screen stops showing the server's answer.** §14: the UI updates optimistically and never
  waits. The projection is derived, not stored (see below), so this costs no new durable state.

## The two questions

M7's brief tabulated **"who may write this?"** for every piece of state, and all four of its review
findings still landed — three were "the right writer at the wrong moment", the fourth was "the
write moved and the rule did not". So this brief answers a second question for every pair of writes
the milestone adds: **which order survives a crash between them, and which invariant guards each
half?**

### Question one — who may write this

The engine is the **third** writer of state that already has two, and the first that runs without a
screen asking it to.

| State | Owner before M8 | What the engine may do | The rule that lets it |
|-------|-----------------|------------------------|-----------------------|
| `order.value` — the canonical snapshot | `adopt`, from `send`/`refetch`/`hydrate` | adopt the snapshot on every answered mutation | `adopt` still refuses a snapshot older than the one held (`acceptsSnapshot`), and the engine adopts only while its terminal claim is current |
| `orders` (Dexie) — the cache | `localStore.saveOrder` | cache every canonical snapshot it receives | monotonic inside the write transaction since the M7 review's round 2; unchanged here |
| `pendingMutations` (Dexie) — the queue | `savePending`/`deletePending`/`setPendingStatus` | insert, relabel, delete, and re-issue on a rebase | **disk is the queue.** The store holds a mirror and never edits it in place — every mutating call is followed by a re-read |
| `queue` — the in-memory mirror | new in M8 | replace it wholesale after any write | it is a projection of the table, never a second copy of the truth; a stale mirror is a display bug, not a correctness one |
| `syncMetadata.currentOrderId` | `saveOrder`/`clearCurrentOrder` | nothing | the pointer is about which order the *screen* is on; the engine syncs every order this terminal queued, including ones the screen has left |
| the pass itself | new in M8 | one at a time | a trigger arriving during a pass sets a flag and the running pass loops again rather than starting a second one — the same shape as `createCoalescingLoader` |
| `pendingByOrder` in `stores/kitchen.ts` | `stores/kitchen.ts` | **nothing** | the engine reads rows by `terminalId`, and every kitchen row carries `KITCHEN_TERMINAL_ID`. The kitchen keeps its single slot per order in M8 |

The engine runs for **the terminal the screen has claimed**, and takes the same generation
`useTerminal`/`releaseTerminal` bump. A pass that finds its claim superseded stops writing to
memory; it does **not** roll back what it already wrote to disk, because those writes record what
the server actually answered and are true regardless of which screen is up.

### Question two — for each pair of writes, which order survives a crash between them

| Pair | The order chosen | What a crash between them leaves | The invariant that makes it safe |
|------|------------------|----------------------------------|----------------------------------|
| optimistic display **+** durable intent | **there is no pair.** The queue row is the only write; the display is `project(canonical cache, queue)`, computed on read | — | the projection is a pure function of two things that are both persisted, so a reload reproduces it exactly. Storing the prediction would create the pair *and* would poison a cache documented as canonical |
| canonical answer cached **+** the row deleted | cache first (M7's rule, unchanged) | a row that outlived its answer | the re-send carries the same `mutationId`, so §9 answers `ALREADY_APPLIED`. The other order loses a `CREATE_ORDER` outright |
| head → `CONFLICT` **+** followers → `BLOCKED` | one Dexie `readwrite` transaction — no window | — | and, independently of the transaction: **the send gate does not trust `status`.** A row is sendable only when no *earlier* row for its order is `CONFLICT`. The labels are for the operator; the derivation is the rule. A crash before the transaction leaves the head `PENDING`, it is re-sent, and it conflicts again — deterministically |
| rebase: old row removed **+** re-issued row inserted | one transaction | — | were it two, **insert first**: two rows are refused by the gate and the operator resolves again, whereas delete-first loses the operator's intent with nothing left to recover it from |
| discard: head deleted **+** followers deleted | one transaction | — | were it two, **followers first**: deleting the head first makes provably stale followers sendable, which is the cascade §14.1 exists to prevent |
| `SYNCING` written **+** the request leaving | status first (M7's rule, unchanged) | a row stuck `SYNCING` forever | `SYNCING` means *this tab, right now* and is therefore **not durable state**: hydration rewrites every `SYNCING` row for this terminal back to `PENDING` before the first pass. M7 only did this on a caught error, which covered the rejection and not the crash |

## Design decisions taken here

**1. The optimistic view is derived, never stored.** `orders` stays what ADR 013 says it is — the
last canonical snapshot the server gave us. The screen renders
`projectQueue(canonical, queueForThatOrder)`. This is what removes the worst write pair in the
milestone, and it makes the reload story trivial: hydrate the cache, hydrate the queue, and the
same three items reappear because the same fold runs again.

**2. `baseVersion` is stamped from the *projected* version, not the canonical one.** Offline, the
client is the only writer, so it can predict the versions the server will produce: a
`CREATE_ORDER` at `baseVersion 0` projects v1, the `ADD_ITEM` behind it is stamped at 1 and
projects v2, and so on. That is why §19.2's four queued mutations all apply on reconnect without
anything being re-stamped — and why §19.3's first mutation conflicts the moment another terminal
has moved the order, which is the correct answer and the whole demo.

**3. The prediction reuses `decide()` and duplicates only the arithmetic.** `@pos/domain`'s
`decide()` is added as a dependency of `apps/web` and answers *may this apply* on the client
exactly as it does on the server, so an optimistic `ADD_ITEM` onto a locally-cancelled order is not
projected. What cannot be shared is the item arithmetic: server-side it is SQL
(`insert … on conflict do update set quantity = quantity + excluded.quantity`), and lifting it into
JavaScript to share it would replace an atomic upsert with a read-modify-write. So the client folds
items itself, in one file, and **the fold is a prediction, never a fact** — every canonical answer
replaces it, and the price it predicts comes from the menu rather than from the order.

**4. Every mutation goes through the queue, online included.** There is no fast path. Online, the
engine is kicked immediately after the enqueue and the row lives for a few hundred milliseconds;
offline it lives until the toggle flips. One code path means the offline demo exercises the same
machinery the normal flow does.

**5. The engine has no timers.** It runs when something happens: after an enqueue, after
hydration, when the socket connects, when `navigator.onLine` goes true, when `Simulate Offline` is
switched off, and when the operator presses **Sync now**. A pass that hits a transport error stops
and waits for the next trigger. A retry loop on a timer would make the demo non-deterministic and
would hide, rather than show, that the client is offline.

**6. `Simulate Offline` intercepts in `apps/web/src/api/client.ts`**, per terminal, and throws an
`OfflineError` from the mutation posts and from `GET /api/orders/:id`. Not in the stores — a store
that knew it was offline would grow a second code path — and not via DevTools, because §14 requires
the demo to be deterministic. **Reads are blocked too**: §19.3 needs POS-1 not to learn that POS-2
cancelled the order, or the queued `baseVersion`s would be re-validated by a refresh the operator
never asked for.

**7. `MUTATION_ID_REUSED` and `REJECTED` halt the aggregate like a `409` does.** §14's engine has
to handle four outcomes and only two of them are success. A reused id with a different payload is
not retryable by definition, so leaving the row `PENDING` would spin; halting surfaces it, and
**rebase is the correct resolution** — it re-issues with a fresh `mutationId`, which is exactly
what the server objected to the absence of.

**8. A rebase re-stamps one mutation at a time, and keeps `createdAt`.** §14.1: A is re-issued at
v6, and only after it applies is B re-issued at v7. So the operator's single **Rebase** action is a
sequential loop, not a batch re-stamp; the fresh `baseVersion` for each step comes from the
canonical order returned by the previous step, not from a refetch. The re-issued row **keeps the
original `createdAt`** so it stays in front of the followers it is still blocking — the same
reasoning `savePending` already applies to a retry. `CREATE_ORDER` is the one exception to the
fresh baseVersion: it is always 0.

**9. A `mutationId` is never regenerated except by a rebase.** Retry, hydration, reconnect and the
engine's own re-sends all reuse the stored id so §9 answers `ALREADY_APPLIED`. The rebase is the
single place §14.1 says a new id is required, and it is driven by a human.

## In scope

1. **`apps/web/src/api/offline.ts`** — the per-terminal offline switch and `OfflineError`;
   `client.ts` consults it in `postMutationTo` (which already carries `terminalId`) and in
   `fetchOrder`, which gains a `terminalId` argument.
2. **`apps/web/src/domain/project-queue.ts`** — the fold: canonical snapshot + queued mutations →
   the order as this device believes it to be, plus the `baseVersion` a new mutation is stamped
   with. Uses `decide()` for legality.
3. **`apps/web/src/sync/engine.ts`** — `createSyncEngine(deps)`: a coalesced pass that reads the
   queue, groups it by order, sends sequentially, applies §14.1, and exposes `rebase(orderId)`.
   Dependency-injected (`post`, `now`, the terminal claim), so §21.7 and §21.8 test it against the
   real repository over `fake-indexeddb` with a scripted server.
4. **Repository additions in `local-store.ts`** — `readQueue`, `normalizeSyncing`, `haltQueue`
   (the one transaction that writes `CONFLICT` + `BLOCKED`), `discardHalted`, `reissue`.
   **No schema change**: `terminalId`, `orderId` and `createdAt` are already indexed, so this stays
   at Dexie version 1.
5. **`stores/order.ts` rewritten around the queue** — `enqueue` replaces `send`; `queue`,
   `pendingCount`, `visibleOrder`, `halted`, `conflictedMutation` and `blockedMutations` replace
   the single slot; `sync`, `discardHalted` and `rebaseHalted` are the actions;
   `identityFor`/`sameMutation` are deleted.
6. **`PosView.vue`** — the `Simulate Offline` toggle, the pending counter, the queue panel, and the
   §14.1 resolution panel showing the canonical state next to the local intent with **Discard** and
   **Rebase**. The item list, the total and the status all read the projection.
7. **Tests** — `sync-engine.test.ts` carrying **§21.7** and **§21.8** named by their spec numbers,
   `project-queue.test.ts`, offline-toggle tests, and the existing store tests updated.
8. **`docs/adr/002-offline-first.md`** — the slot the ADR index has reserved for this decision since M0 — the derived projection, the projected `baseVersion`, and
   why nothing auto-resolves.

## Out of scope

- **No server change.** The engine speaks the §5 endpoints as they are. §9, §8 and the §17
  envelope already answer everything it needs.
- **The kitchen keeps its single slot per order.** It already halts at the aggregate; giving it the
  queue as well is not what §21.8 asks for and would double the surface of this milestone.
- **No `/debug` counters.** §19.3 ends "`/debug` shows every version and mutationId" — that is
  M11's page, and M8 shows the same facts on the POS instead.
- **No failure-simulator page.** `Simulate Offline` lives on the POS header in M8; M12 moves the
  eleven controls of §18 onto `/debug`.
- **No timer-driven retry, no exponential backoff on the client.** M9 is the backoff milestone and
  it is server-side.

`pnpm verify:integration` must stay green; nothing in this milestone touches a server file.

By hand, with Compose up:

- **§19.2** — POS-1, `Simulate Offline` on. Create an order, add a Burger, add a Coffee, change a
  quantity. The screen shows all of it, the badge says `4 PENDING`, nothing has reached the server.
  Toggle offline off. The queue drains in order, the counter reaches zero, and the order on screen
  is the server's.
- **§19.3** — POS-1 and POS-2 both on the same order at v5. POS-1 offline, queue three mutations.
  POS-2 cancels the order; the server reaches v6. POS-1 back online: the first mutation returns
  `409 ORDER_CANCELLED`, the other two are `BLOCKED` and are never sent, and the POS shows the
  canonical cancelled order beside the three local intents with **Discard** and **Rebase**.
  Discard empties the queue; Rebase re-issues the first, which conflicts again on a cancelled
  order, leaving the rest blocked — §14.1's own example.
- **§21.8's other half** — offline, queue mutations for order A, press **New order** and queue
  mutations for order B, then come back online with POS-2 having moved A underneath it. A halts, B
  syncs, and the POS says another order is halted with a way back to it. (New commands are refused
  while the order **on screen** is halted, so this is reached by leaving A before it conflicts, not
  after — a halted order is resolved, not walked away from.)
