# M22 — The flag path, end to end

The second of the four grouped sweeps (`MILESTONES.md`, *The second sweep*). It takes the five
backlog entries that live on the **feature-flag path** — the Redis cache in front of
`feature_flags`, the store behind `/debug`'s panel — plus the three entries whose honest answer is
an argument rather than a patch.

§15 promises one sentence: *the toggle is fleet-wide and immediate, and takes effect without a
restart.* Two of the five say that sentence is not quite true. The other three say something that
was already decided is a defect. Both kinds are closed here.

## Scope

Five lines from `docs/known-problems.md`, gone from it when they are closed.

1. **`[M13, P2]` a cache-aside fill can overwrite an invalidation.** A request that missed reads
   the flag rows and then fills the cache. If `POST /api/debug/flags/:key` commits and invalidates
   while that read is in flight, the late fill puts the **pre-toggle** rows back for one
   `FLAG_CACHE_TTL_MS`, and a client polling `/api/config` keeps its old transport for another
   interval. So §15's "immediate" is false inside that window.
   **Fix:** a versioned fill. A miss carries the cache version it saw; the fill presents it, and a
   fill whose version has moved is discarded rather than written.
2. **`[M20, P3]` `flags.busy` holds one key.** Two overlapping toggles leave the first switch
   enabled while its own request is still out — the exact defect M20 fixed in the simulator store
   and did not fix here. `FlagPanel.vue:71,99` read it.
   **Fix:** the same three lines as `stores/simulator.ts` — a `Set` and an `isBusy(key)`.
3. **`[M19, P3]` mark-then-emit in the realtime consumer**, **`[M19, P3]` the
   `TimeoutNegativeWarning` from a dependency**, **`[M20, P3]` a resolution reported offline is
   never recorded.** Each is re-argued once and then either moved into *Accepted limits* or
   deleted. None of the three is a code change: they were filed as defects and each already
   carries, in its own text, the reason it is not one.

## Out of scope, and why

- The two `[M21, P3]` lines (the port probe's position; the overlay's hand-run first boot). They
  are deployment and harness surface — M24.
- The M16/M17 lines. They are the browser surface — M23.
- **Making the fill a lock or a single-flight.** A stampede of concurrent misses all reading the
  same rows and all filling the same key is harmless: the table read is cheap, the value is
  identical, and no entry asks for it. The bug is a *stale* fill, not a *repeated* one.
- **Serving the cache under a lock so a toggle is atomic across instances.** The invalidation is
  one Redis command and the read is one; there is nothing to serialise once a stale fill can no
  longer land.

## Key decisions

- **The version lives beside the value and is compared on read, not deleted on write.** The stored
  payload carries the version it was filled at; `invalidate()` is a single `INCR` of a separate
  key. A payload whose version no longer matches reads as a miss, so a stale fill is not merely
  refused — it is unreachable even if it lands. One round trip (`MGET` of the two keys), no Lua, no
  `WATCH`/`MULTI`, and two instances toggling at once cannot leave either one's value cached.
- **The port carries the version, not the Redis client.** `loadFlags` threads an opaque string from
  the miss to the fill and never interprets it, so `buildApp()` without a cache is unchanged and
  every `fastify.inject` test stays free of infrastructure (ADR 006).
- **`createRedisFlagCache` takes the three commands it uses, not `Redis`.** A narrow structural
  parameter is what lets the falsifying test drive the *real* cache with an in-memory double — and
  keeps the rule that a unit test in this repository never needs a live Redis.
- **A cache read that threw does not fill.** No version was observed, so there is nothing to
  present; the request answers from the table and the next miss fills. Failing closed is right
  here: the whole entry is about a fill that should not have happened.
- **The three re-argued entries move rather than vanish.** Each is a property worth saying out loud
  in the interview — a bounded loss window §12.2 chose, a warning that is not ours, an
  observability field that is best-effort by design. A deleted line is a fact nobody can find
  again.

## Verification

- `pnpm lint`, `pnpm typecheck`, `pnpm -F @pos/api test test/flags.test.ts`,
  `pnpm -F @pos/web test test/flag-store.test.ts`, `pnpm test`, `pnpm build`,
  `pnpm verify:integration`.
- **Each fix has a test that fails without it**, which is the M21 standard and the point of this
  milestone as much as the fixes are:
  - the API test drives `createRedisFlagCache` against an in-memory double, pauses a fill across a
    concurrent `invalidate()`, and asserts the next read is a **miss**. Reverting to an
    unconditional `SET` reddens it.
  - the web test calls `update()` twice in one tick against two never-resolving requests and
    asserts `isBusy` is true for **both** keys. Reverting to a single-key `busy` reddens it.
- `docs/known-problems.md` holds ten backlog lines afterwards, none of them M13, M19 or M20.

## Definition of done

The five lines are gone from `docs/known-problems.md` — two deleted because the code changed,
three moved into *Accepted limits* because the argument, made once, says the behaviour is right.
The commands above are green, both fixes are falsified rather than merely green, and the ADR names
the versioned fill so the next reader does not re-derive it.
