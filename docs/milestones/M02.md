# M2 — Database schema, migrations, and seed data

**Model:** Opus. **Size:** M. **Previous:** M1 (monorepo, Compose, three processes).
**Demoable after:** no — there is still no business logic, only a database that later milestones
build on.

## Goal

All thirteen tables from §4 exist as Drizzle definitions, a generated SQL migration applies to a
clean database, and `pnpm db:seed` loads the reference data every later milestone assumes:
two restaurants, four terminals, seven products, and the `realtime.websocket_push` flag.

The schema is written **once, in full**. Later milestones read and write these tables; they do not
reshape them. That is why M2 includes columns nothing uses yet — the outbox lease, `print_jobs`,
`conflict_log` — instead of growing the schema milestone by milestone.

## In scope

### 1. Drizzle wiring in `apps/api`

- Dependencies: `drizzle-orm` and `pg` (node-postgres); `drizzle-kit` and `@types/pg` as dev
  dependencies.
- `apps/api/drizzle.config.ts` — schema path, `out: './drizzle'`, dialect `postgresql`,
  credentials from `@pos/config` (never `process.env` directly, per the M1 rule).
- `apps/api/src/db/schema.ts` — every table in one file. The schema is a single cross-cutting
  artifact; splitting it per module would hide the foreign keys that tie the modules together.
- `apps/api/src/db/client.ts` — a `pg.Pool`, the Drizzle instance, and a `closeDb()` the scripts
  call so they exit cleanly.
- Scripts in `apps/api/package.json`, proxied from the root: `db:generate` (drizzle-kit generate),
  `db:migrate`, `db:seed`, `db:check`. The M1 placeholders that exit with "M2 not implemented"
  are replaced.

### 2. The thirteen tables (§4)

`restaurants`, `terminals`, `products`, `orders`, `order_items`, `payments`,
`processed_mutations`, `outbox_events`, `processed_events`, `kitchen_tickets`, `conflict_log`,
`feature_flags`, `print_jobs`.

Points that are decisions, not transcription:

- **Identifiers.** `restaurants`, `terminals` and `products` use readable slug text ids
  (`demo-restaurant`, `pos-1`, `burger`), because §5's own protocol example carries
  `"terminalId": "pos-1"` and `"productId": "burger"`, and because a debug screen full of UUIDs
  teaches a reviewer nothing. Everything generated at runtime — `orders.id`, `order_items.id`,
  `payments.id`, `outbox_events.id`, `conflict_log.id`, `print_jobs.id` — is `uuid`.
- **`outbox_events.id` is the `eventId`** of the §11 envelope. There is no second identifier to
  keep in sync, and `processed_events.event_id` refers to exactly this value.
- **`outbox_events.restaurant_id` and `trace_id` are added** beyond §4's list. §11 requires
  `restaurantId` and an optional `traceId` in the published envelope, and the publisher runs
  outside the mutation transaction, so those values must live on the row rather than be
  reconstructed by joining back to `orders` at publication time.
- **`order_items` carries `unique(order_id, product_id)`.** One product is one line whose quantity
  changes, which makes `ADD_ITEM` an upsert and gives `CHANGE_QUANTITY` and `REMOVE_ITEM` a stable
  target. §8's "concurrent quantity change to the same item" assumes that identity. No modifiers
  or per-line notes are in scope, so nothing needs two lines of the same product.
- **`payments.mutation_id` is unique** — the physical guarantee behind §21.9: a repeated `PAY`
  cannot insert a second payment even if the idempotency check above it were bypassed.
- **`order_status` is a PostgreSQL enum**, built from a single `ORDER_STATUSES` tuple exported by
  `packages/contracts`, so the database and `OrderStatus` cannot drift.
  `kitchen_tickets.state`, `print_jobs.state` and `conflict_log.resolution` stay `text`: they are
  projection and infrastructure states owned by consumers that later milestones still shape, and
  changing an enum value costs a migration.
- `processed_mutations.mutation_id` is the primary key — both the uniqueness requirement of §9 and
  the index §4 asks for.
- `processed_events` has the composite primary key `(event_id, consumer_name)` — §12's requirement,
  and again the index §4 asks for.
- Money is `integer` cents everywhere: `products.price_cents`, `order_items.unit_price_cents`,
  `orders.total_cents`, `payments.amount_cents`.
- Timestamps are `timestamptz`.
- Foreign keys: `terminals → restaurants`, `orders → restaurants`, `order_items → orders`
  (`on delete cascade`) and `order_items → products`, `payments → orders`,
  `kitchen_tickets → restaurants`. `outbox_events.aggregate_id`, `conflict_log.order_id` and
  `processed_mutations.order_id` are deliberately **not** foreign keys: an append-only event log,
  an audit record, and an idempotency record must survive independently of the row that produced
  them.

### 3. Indexes — only the intentional ones (§4)

- `orders(restaurant_id)` and `orders(status)`.
- `outbox_events(next_attempt_at)` **partial**, `where published_at is null and
  dead_lettered_at is null` — the publisher's only query, and the reason the table stays fast once
  it holds a million published rows.
- `kitchen_tickets(restaurant_id, state)`.
- `terminals(restaurant_id)`, because the seed and the debug screen both list terminals per
  restaurant.
- Nothing else. Primary keys and unique constraints already cover `processed_mutations` and
  `processed_events`.

### 4. Migration

`pnpm db:generate` produces `apps/api/drizzle/0000_*.sql` plus its journal, and both are
**committed**. `pnpm db:migrate` applies pending migrations through
`drizzle-orm/node-postgres/migrator` and exits non-zero on failure. No `db:push`: a demo about
durability does not get to skip migration files.

### 5. Seed (`pnpm db:seed`) — idempotent

- Restaurants: `demo-restaurant` "Demo Restaurant", `second-restaurant` "Second Restaurant".
- Terminals: `pos-1`, `pos-2`, `bar-1` in the first; **`pos-3` in the second** — required by the
  cross-tenant test (§21.11) and the per-restaurant flag rollout (§15).
- Products, in cents: Burger 1200, Cheeseburger 1400, Pizza 1500, Caesar Salad 1000,
  French Fries 500, Cola 300, Coffee 400.
- Feature flag `realtime.websocket_push`: `enabled = true`, `rollout_percent = 100`.
- Reference rows use `onConflictDoUpdate`, so corrected names and prices propagate on a re-run.
  The feature flag uses `onConflictDoNothing`: once `/debug` can toggle it (M13), a re-seed must
  not silently re-enable a flag an operator turned off.
- The seed touches no order data and deletes nothing.

## Out of scope

The mutation handler, any HTTP route beyond the existing health stubs, the domain package, the
outbox publisher, consumers, Vitest and integration-test infrastructure (M3 and M6), the UI.
No table gains a column for a feature whose milestone has not been read.

## Verification

Claude runs, against the PostgreSQL the user already has up:

```bash
pnpm typecheck
pnpm lint
pnpm build
pnpm db:migrate
pnpm db:seed
pnpm db:seed
pnpm db:check
```

Expected:

- `db:migrate` applies the migration and reports success; a second run reports nothing to apply.
- `db:seed` run twice leaves the same row counts — 2 restaurants, 4 terminals, 7 products,
  1 feature flag — which is what "idempotent" means here.
- `db:check` selects from all thirteen tables, prints a row count for each, and additionally
  prints the `orders` column list and confirms the partial outbox index exists, so the shape can
  be inspected without a psql session. It exits non-zero if a table or the index is missing.
- `pnpm typecheck`, `pnpm lint` and `pnpm build` stay green.
